# 90-1 插件设计需求

> 设计定案（清单/目录/贡献/面板 schema/状态栏标签策略）：`90-2-插件清单与贡献规范.md`（2026-10-18）。

PF 本身由三块构成 ——
1、基于 Pi 的对话功能
2、基于 Pi 的会话管理
3、基于文件系统的文件管理和编辑

可以看出第三点和前两点毫无关系，PF 的插件因此有两类天然取向：专注于文件管理、
版本管理（与 Pi 会话无关），以及需要介入对话/会话的。插件框架必须同时容纳两者，
并考虑插件的最高自由度。插件对宿主的能力诉求，按抽象能力陈述：

1、与 Pi 通信：在会话进程中执行、向会话注入输入、订阅会话事件
2、在对话中定制渲染：消息需要额外的来源标记（「渠道」语义），反映为会话内的定制渲染
3、拥有自己的面板：自绘内容（例如展示宿主之外服务的状态）
4、像系统组件一样可被启用/关闭
5、拥有独立设置：启用时随 PF 启动加载；复杂设置页归插件自身实现，降低 PF settings 的耦合度和复杂度
6、（深度场景）介入 editor 等既有模块：宿主需评估开放编辑处理接口与渲染接口

基于以上诉求，对 PF 插件（以下简称 PFP）的实现需求总结如下：

1、PFP 可以成为 Pi 的 extension
2、PFP 可以在对话中有定制的渲染卡片（待定）
3、PFP 可以有自己的面板（当前 PF 只有一个项目管理面板）
4、PFP 可以拥有自己的标签页（复杂管理界面场景）
5、PFP 可以有独立设置，启用时随 PF 启动加载进系统
6、PFP 需要统一的 log 规范，便于 PF 进行管理和问题诊断
7、PFP 需要市场/安装界面
8、学习 Pi，对插件做安全管理
