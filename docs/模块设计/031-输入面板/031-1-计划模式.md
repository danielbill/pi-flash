# 031-1 计划模式

## 功能需求（已申明，原文保留）

参照 zcode，在工具列表菜单顶部增加一项 「计划模式」，分隔线与下方工具选项分隔。
在计划模式下 ——
- agent不得修改文件
- agent知道自己在计划模式下，应当和用户讨论工作计划
- agent在完成用户指令后，给出计划方案
- 计划用模态弹窗，占会话区 100%高度 100%宽度，完全占据用户注意力，上方80%空间用来呈现计划，使用editor - markdown priview渲染方式（复用而不是搓新代码）
- 下方操作面板居中，宽度600px：
  - 第一行长按钮：批准计划，取消计划模式
  - 第二行长按钮：否决/取消（Esc）
  - 第三行长输入框：placeholder：输入其他想法； 用户按回车发送
- 批准操作将取消计划模式
- 否决/取消，直接取消计划弹窗，中止agent等待，计划模式依旧，用户在输入框输入其他想法，谈话继续
- 输入其他想法回复agent，计划模式依旧，agent重新计划

## 1. 架构总览

工具在 pi 进程内执行（RPC 模式无宿主审批回调，`docs/security.md` 明言"每次工具调用前不询问"），
**闸门必须住在 pi 进程里 = pi 扩展（JS asset），PF 插件（Rust→wasm）体系没有 tool_call 拦截位**
（wasm 载体铁律约束的是 090-4 PF 插件；本模块走 041 pi 扩展体系，与 `full_activate.ts` 同分发机制）。

pi 1.5.0 四个必需原语全部就位（vendor `pi-coding-agent`）：

| 能力 | 原语 | 依据 |
| --- | --- | --- |
| 执行前拦截 | `pi.on("tool_call")` → `{block, reason}`，handler 出错也 block（fail-safe） | `dist/core/extensions/types.d.ts:1108-1117` |
| 每轮提醒注入 | `pi.on("before_agent_start")` → 返回 `message` 前置本轮上下文 | `types.d.ts:1144-1148` |
| 阻塞等待宿主决定 | 自定义工具 handler 挂起 + `ctx.ui` / abort signal | `examples/extensions/plan-mode/index.ts` 官方模板 |
| 扩展⇄PF 通道 | PF→ext：`prompt "/plan"` 扩展命令（流式中也立即执行）；ext→PF：`setStatus` fire-and-forget | `docs/rpc-commands.md:31`；pi-link `ExtUiMethod::SetStatus` 已解析 |

```text
┌─ PF (GPUI) ──────────────────────────────────────────────┐
│ 工具菜单「计划模式」勾选 ──prompt /plan──────────┐        │
│ 计划审批弹窗（会话区 100%×100%，markdown 预览）  │        │
│   批准 ──prompt /plan-approve───────────┐        │        │
│   否决 ──Abort + ClearQueue─────────────┤        │        │
│   其他想法 ──prompt /plan-reject + 正文 prompt──┤  │        │
│                                         │        │        │
│ 状态投影 ←─setStatus("pf-plan", JSON)────────────┼──┘      │
│ 弹窗触发 ←─tool 事件 present_plan(args)─────────┘         │
└──────────────┬───────────────────────────────────────────┘
               │ RPC（现有 wire，零协议改动）
┌──────────────▼───────────────────────────────────────────┐
│ plan_mode.ts（随包 asset 扩展，-e 全档位装载）             │
│  registerCommand("plan")           切换计划状态           │
│  registerTool("present_plan")      handler 挂起等批准     │
│  tool_call 硬闸                    block edit/write/危险bash │
│  before_agent_start                注入计划模式提醒        │
│  appendEntry / session_start       持久化 + 冷恢复广播      │
└──────────────────────────────────────────────────────────┘
```

## 2. 关键设计裁决

1. **扩展是唯一事实源，PF 是投影**（ZCode todo-151 的教训反向应用）：
   PF 菜单点击只发 `/plan`，成功与否以扩展 `setStatus("pf-plan")` 广播为准；
   `session_start` 时扩展广播当前状态 → 会话切换/分支/冷恢复零 PF 持久化成本。
   严禁 PF 本地猜状态后覆盖（历史授权重放 bug 的 ZCode 前车之鉴）。
2. **无工具集切换、无快照恢复**（2026-11-08 用户裁决）：工具集从头到尾
   就是原工具选项，计划模式只是 tool_call 把写操作打回；批准 = 仅清除
   planEnabled。不做内置工具的 `setActiveTools` 切换，也不碰 PF 的
   `tools_preset` 档位字段（spawn 配方语义不动）。**2026-11-09 精化**：
   唯一例外是 present_plan 的模型声明随计划态收放（见裁决 8），内置工具
   集仍然恒定。
3. **纯 block，不摘工具**：tool_call 硬闸是唯一执行点（本轮已发出的并行
   tool call 只有它能拦）；被 block 以 error tool result + reason 回给模型，
   模型自行转向只读探索（ZCode 同款 deny 语义）。
4. **计划呈现 = 自定义工具 `present_plan`**（ZCode ExitPlanMode 同款：正文在工具参数里，
   模型无"计划文件"概念）：扩展注册工具，handler 存下 plan 正文、广播 PF 开弹窗、
   挂起等待裁决（race abort signal）；工具结果 = 裁决内容，agent 原地继续。
5. **弹窗两动作（2026-11-08 简化裁决：去掉输入框）**：
   - 批准 → `/plan-approve`：扩展关计划（工具集未动过，无需恢复），resolve present_plan 为"已批准开始执行"，agent 同一轮继续实现（无需新 prompt）；
   - 否决/取消（按钮与 Esc 键、标题 × 同一路径）→ 关弹窗 + `Abort`+`ClearQueue`
     配对（铁律：abort 不清队列）→ **取消即停**（无收尾发言轮，
     2026-11-08 终版裁决；此前 resolve 通道会让模型多跑一轮收尾发言）；
     模型视角反馈由扩展 `context` 钩子把中止错误结果改写为「用户拒绝或
     取消了你的计划」（已查证：`tool_result` 钩子无 terminate，abort +
     请求时改写是唯一组合）；
   - 用户的新想法直接在 composer 输入（弹窗无输入框），零阻断。
6. **计划态拦截面（2026-11-08 用户裁决，推翻 v1 保守 default-deny）**：只拒绝
   「修改」本身——`edit`/`write` 一律 block；`bash` 按破坏性黑名单命中才
   block（缺省放行）；**其余工具全部放行**——压缩/Provider（freeflow）/
   子代理委派/MCP 等扩展生态不下掉（切只读工具集会让 free 模型直接不可用）。
   残留风险：bash/python 间接写可漏（缺省放行的代价），edit/write 硬闸是
   主防线，提醒文案同时约束「不得借其他工具绕过」。
7. **`/plan` 防哑弹**：扩展命令若因 `-e` 装载失败未被消费，pi 会把 `/plan` 当普通
   消息发给模型（`disposition:"started"` 而非 `"handled"`）。PF 发送后必须校验
   response disposition，未 `handled` → toast 报错 + 回滚乐观勾选。
8. **present_plan 注册恒在，模型声明随计划态收放**（2026-11-09 用户裁决，
   精化原「常驻声明 + guard」）：
   - **注册必须恒在**：`--tools` 白名单是注册前提（不点名永不注册）；
     pi 的注册门与激活门不可分——白名单分支会无条件激活一切点名工具
     （agent-session.js："Naming or matching a tool activates it even when
     it is not active by default"），`defaultActive:false` 救不了。
   - **声明靠扩展主动收放**：`syncToolExposure()` 在 session_start（恢复
     后对齐）、`/plan` handler（翻转即同步，no-op 翻转也跑 = 自愈）、
     批准路径三处调 `pi.getActiveTools()/setActiveTools()`（有差才调——
     setActiveTools 每调一次重建系统提示词，无条件调 = 提示词缓存失效）。
     RPC 命令 handler 里这对 API 实测可用（appendEntry unbound 前科不
     适用于它们，探针 2026-11-09）。
   - **execute 内 guard 保留兜底**：取/设失败或时序缝隙（如同轮残留声明）
     时调用仍被拒，不会出现非计划态真执行。

## 5. 风险与陷阱

- **disposition 校验（裁决 7）**是唯一会造成"静默发错消息"的点，必须做。
- **扩展命令 handler 里 `pi.appendEntry` 会抛错**（RPC 模式实测：runtime action
  未绑定）——持久化一律走 `ctx.sessionManager.appendCustomEntry`（plan_mode.ts
  `persist()` 已按此实现，探针留档）。
- **草稿期勾选的同步窗口**：spawn 后 session_start 广播（false）先于同步
  命令的广播（true）到达——`plan_sync_pending` 期间相反广播必须忽略，否则
  用户勾选被闪掉（pif-ui 实测路径见 P4）。
- **焦点仲裁是白名单制**（shell/render/focus.rs else-if 链，末级「回家」
  分支逐帧抢回 composer）：自造 FocusHandle 的浮层不在名单里 → Esc 与
  输入框全部失灵（真机实锤后返工）。新浮层要么复用 `dlg.dialog_focus` +
  在仲裁链加分支，要么走 `DlgUi.dialog` 老枚举——禁自造焦点句柄。
- **Abort 打断工具执行时 pi 把整轮标 stopReason=error**（errorMessage=
  "This operation was aborted"）——PF 侧按 `Msg::is_abort_error` 并入内部
  中断口径（黄点、无红框；turn/render final_error 与 live 通知点两处同
  口径）。此为通用修复：停止键打断任何工具执行同款受益。
- **MSYS 路径改写**：Git Bash 下 `pif-ui exec --arg text="/plan"` 会被改写成
  `C:/Program Files/Git/plan`（整条命令静默发给模型！）——自动化传斜杠文本
  一律走 `--params-file`。
- 无真实消息前 pi 不落盘会话文件（探针实测 ENOENT）——冷恢复探针须手工会话
  文件驱动；PF 真实使用中文件必然存在，不受影响。
- Abort 必配 ClearQueue（既有铁律），否则排队消息在下一轮被冲出来重放。
- present_plan handler 必须 race `ctx.signal`，否则 abort 后 handler 永悬。
