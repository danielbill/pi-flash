# 031-1 计划模式

## 功能需求（已申明，原文保留）

参照 zcode，在工具列表菜单顶部增加一项 「计划模式」，分隔线与下方工具选项分隔。
在计划模式下 ——
- agent不得修改文件
- agent知道自己在计划模式下，应当和用户讨论工作计划
- agent在完成用户指令后，给出计划方案
- 计划用模态弹窗，占会话区 90%高度 90%宽度，完全占据用户注意力，上方80%空间用来呈现计划，使用editor - markdown priview渲染方式（复用而不是搓新代码）
- 下方操作面板居中，宽度500px：
  - 第一行长按钮：批准计划，取消计划模式
  - 第二行长按钮：否决/取消
  - 第二行长输入框：placeholder：输入其他想法； 用户按回车发送
- 批准操作将取消计划模式，回到用户启用计划模式前的工具集（切换到计划模式时，要存储之前的工具选项）
- 否决/取消，直接取消计划弹窗，中止agent等待，计划模式依旧，用户在输入框输入其他想法，谈话继续
- 输入其他想法回复agent，计划模式依旧，agent重新计划

---

## 1. 架构总览

工具在 pi 进程内执行（RPC 模式无宿主审批回调，`docs/security.md` 明言"每次工具调用前不询问"），
**闸门必须住在 pi 进程里 = pi 扩展（JS asset），PF 插件（Rust→wasm）体系没有 tool_call 拦截位**
（wasm 载体铁律约束的是 090-4 PF 插件；本模块走 041 pi 扩展体系，与 `full_activate.ts` 同分发机制）。

pi 1.5.0 四个必需原语全部就位（vendor `pi-coding-agent`）：

| 能力 | 原语 | 依据 |
| --- | --- | --- |
| 执行前拦截 | `pi.on("tool_call")` → `{block, reason}`，handler 出错也 block（fail-safe） | `dist/core/extensions/types.d.ts:1108-1117` |
| 每轮提醒注入 | `pi.on("before_agent_start")` → 返回 `message` 前置本轮上下文 | `types.d.ts:1144-1148` |
| 阻塞等待宿主决定 | 自定义工具 handler 挂起 + `ctx.ui` / abort signal | `examples/extensions/plan-mode/index.ts` 官方模板 |
| 扩展⇄PF 通道 | PF→ext：`prompt "/plan"` 扩展命令（流式中也立即执行）；ext→PF：`setStatus` fire-and-forget | `docs/rpc-commands.md:31`；pi-link `ExtUiMethod::SetStatus` 已解析 |

```text
┌─ PF (GPUI) ──────────────────────────────────────────────┐
│ 工具菜单「计划模式」勾选 ──prompt /plan──────────┐        │
│ 计划审批弹窗（90%×90%，markdown 预览）           │        │
│   批准 ──prompt /plan-approve───────────┐        │        │
│   否决 ──Abort + ClearQueue─────────────┤        │        │

│                                         │        │        │

│ 弹窗触发 ←─tool 事件 present_plan(args)─────────┘         │
└──────────────┬───────────────────────────────────────────┘
               │ RPC（现有 wire，零协议改动）
┌──────────────▼───────────────────────────────────────────┐
│ plan_mode.ts（随包 asset 扩展，-e 全档位装载）             │
│  registerCommand("plan")           切换 + setActiveTools  │
│  registerTool("present_plan")      handler 挂起等批准     │

```

## 2. 关键设计裁决

1. **扩展是唯一事实源，PF 是投影**（ZCode todo-151 的教训反向应用）：
   PF 菜单点击只发 `/plan`，成功与否以扩展 `setStatus("pf-plan")` 广播为准；
   `session_start` 时扩展广播当前状态 → 会话切换/分支/冷恢复零 PF 持久化成本。
   严禁 PF 本地猜状态后覆盖（历史授权重放 bug 的 ZCode 前车之鉴）。
2. **不记「计划前档位」改写用户选择**：扩展在 `/plan` 时快照
   `pi.getActiveTools()`，批准后原样恢复——满足需求"存储之前的工具选项"，
   且不碰 PF 的 `tools_preset` 档位字段（spawn 配方语义不动）。
3. **block 而非摘工具为主，切工具集为辅**：`setActiveTools` 官方语义"下轮生效"，
   本轮已发出的并行 tool call 拦不住——tool_call 硬闸是唯一可靠执行点；
   摘工具只是减少模型困惑的辅助。被 block 以 error tool result + reason 回给模型，
   模型自行转向只读探索（ZCode 同款 deny 语义）。
4. **计划呈现 = 自定义工具 `present_plan`**（ZCode ExitPlanMode 同款：正文在工具参数里，
   模型无"计划文件"概念）：扩展注册工具，handler 存下 plan 正文、广播 PF 开弹窗、
   挂起等待裁决（race abort signal）；工具结果 = 裁决内容，agent 原地继续。
5. **三按钮语义到通道的映射**：
   - 批准 → `/plan-approve`：扩展关计划+恢复工具快照，resolve present_plan 为"已批准开始执行"，agent 同一轮继续实现（无需新 prompt）；
   - 否决/取消 → 关弹窗 + `Abort`+`ClearQueue` 配对（铁律：abort 不清队列）→ present_plan 随 abort 取消，计划模式保持；
   - 其他想法回车 → 先 `/plan-reject`（resolve present_plan 为"用户否决，等待新输入"，run 自然收尾）再发正文 prompt（pi 原子排队），计划模式保持，agent 重新计划。
   - 输入框回车不走 Abort：用 resolve 让本轮干净结束，避免 abort 噪声。
6. **计划态拦截面（v1）**：`edit`/`write` 一律 block；`bash` 按只读白名单
   （移植官方 `isSafeCommand` 思路，清单进 testcase 固化）；**其余非内置只读工具
   （含 MCP）v1 一律 block**——需求底线是"不得修改文件"，外部副作用工具保守处理
   （§5 待决策 3 可放宽）。`read`/`grep`/`find`/`ls` 直通。
7. **`/plan` 防哑弹**：扩展命令若因 `-e` 装载失败未被消费，pi 会把 `/plan` 当普通
   消息发给模型（`disposition:"started"` 而非 `"handled"`）。PF 发送后必须校验
   response disposition，未 `handled` → toast 报错 + 回滚乐观勾选。
8. **present_plan 常驻注册 + handler 内 guard**：非计划态调用直接 error result
   （"仅计划模式可用"），避免动态注册/注销的时机复杂度。

## 5. 风险与陷阱

- **disposition 校验（裁决 7）**是唯一会造成"静默发错消息"的点，必须做。
- Abort 必配 ClearQueue（既有铁律），否则排队消息在下一轮被冲出来重放。
- `setActiveTools` 下轮生效 → 硬闸兜底不可省。
- present_plan handler 必须 race `ctx.signal`，否则 abort 后 handler 永悬。
- full 档 `--tools` 注册级 allowlist：plan 只读白名单若超出注册集，setActiveTools 静默无效（tools_recipe A–H 组实测结论）。
- 提交纪律：窄路径 add 本清单文件；`ui/overlay.rs`、`compose.rs` 等有他人未提交改动，禁扫入；pre-commit rustfmt + 提交后 `git status --porcelain` 验净。
