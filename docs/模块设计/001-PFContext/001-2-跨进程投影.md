# 001-2 跨进程投影：ext-context.json

> 状态：设计定稿，S3 实现。
> 前置：[001-0-PFContext总体设计](001-0-PFContext总体设计.md)。设置文档形态见 [001-1-settings正式化](001-1-settings正式化.md)。

## 1 为什么必须有投影（进程边界）

扩展跑在 pi 子进程（Node），看见的是文件与 env：

- **看不见 PF 内存**：`Hub` 里的 section 对扩展不存在。
- **看不见 DB**：就算将来上 SQLite，也不该让扩展直连（schema 是 PF 内部事务）。
- **env 是启动快照**：这正是 2026-11-08 容量 bug 的第三个 owner——改了要重启，且仍被文件压过。

所以跨进程只有两条路：env（只适合**启动期不变**的路径）与文件（适合**运行期会变**的策略值）。
策略值一律走文件——一份索引文件，而不是让每个扩展自己猜该读哪个 json。

## 2 形态

`<PF数据目录>/ext-context.json`

```json
{
  "version": 1,
  "generated_at": "2026-11-08T08:20:00Z",
  "subagents": { "capacity": 10, "max_depth": 1, "enabled": true },
  "market": {},
  "remote_control": {}
}
```

- 只含**扩展需要**的段；段名 = `Section::KEY`，字段 = 该 section 的 `exportable` 子集。
- `version`：投影格式版本，扩展据此决定回退行为（不匹配 = 视为不可用）。
- `generated_at`：扩展排查「读到的是旧档」的唯一依据。
- 顶层不带 `settings` 包裹：扩展按段名直取，减少一层猜。

## 3 写入

- 由 `SettingsStore` 在**段内容变化后**触发（哈希比较），debounce 50ms，合并连续改动。
- 原子写：同目录 `ext-context.json.tmp<pid>` + rename。
- 内容与盘上一致则跳过（避免 watcher 自身回环）。
- 白名单：只有 `exportable` 的 section 出现；`generate` 时二次过滤，**不依赖 section 自觉**。
- PF 是唯一写者；扩展**禁止回写**投影（会与 hub 的 last-writer-wins 打架）。

## 4 扩展读取契约

- **时机**：`agent` 工具 `execute` 入口读一次（`extensions/pf-subagents/src/index.ts:412` 的 `syncModuleConfig` 位置）。不在流式输出、渲染、每次工具调用的热路径上。
- **成本**（本机实测，5000 次 `readFileSync + JSON.parse`）：平均 90.5µs、最差 1508.1µs。相对一次委派（起子进程 + 一轮 LLM，秒级）占比约 0.003%，无需缓存文件 mtime。
- **回退链**（顺序固定）：
  1. 读投影成功且 `version` 匹配 → 用该段；
  2. 投影缺失 / 坏档 / 版本不匹配 → **保持现值**（不覆盖正在跑的上限），记 `problem`；
  3. 首次启动完全无投影 → 读 legacy `agents/config.json`；
  4. 再无 → 扩展内置 `FALLBACK_MODULE_CONFIG`（capacity 默认 8）。
- **坏档不静默改行为**：`module-config.ts` 现有语义——`loadModuleConfig` 返回带 `problem` 的结果，`syncModuleConfig` 里 `if (!result.problem) applyModuleConfig(...)`，投影实现必须沿用。
- 读取要容忍半文件（原子 rename 下理论上不会发生，但 Windows 杀软/同步盘会），`JSON.parse` 失败即走回退链。

## 5 env 白名单

只剩**路径类 bootstrap**（进程启动前就要知道，且不该变）：

| env | 用途 |
|---|---|
| `PI_SUBAGENTS_PROFILES_DIR` | 子代理 profile 目录 |
| `PI_FLASH_DIR` | PF 数据目录（显式指定优先） |
| `PI_FLASH_PI_BIN` | 开发期覆盖内置 pi |

- **策略值（容量/深度/开关）一律不得走 env**：本次 bug 已证明 env 与文件双写必然分叉。
- `PI_SUBAGENTS_CAPACITY` / `PI_SUBAGENTS_MAX_DEPTH` / `PI_FLASH_APP_SETTINGS` 只保留给**旧版扩展**兼容一个版本，投影上线后从 spawn 环境里移除。

## 6 安全与卫生

- 白名单导出，默认拒绝：section 不声明 `exportable` 就不出现在投影里。
- **永不出现在投影**：api key、oauth token、keyring 引用、`auth.json` 任何字段（051 / 042-1 边界）。
- 不含 PII：投影只放数字/布尔/枚举与用户显式设置的短字符串。
- 文件权限沿用 PF 数据目录默认；投影不加密（无秘密），但也不放可反推凭据的指纹。

## 7 观测与排障

- `hub.dump()` → `<PF数据目录>/context-dump.json`（并入现有同名概念）：
  每 section 的生效值、来源层（L0/L1/L2/L3/L4）、最近写入时间、最近重载时间、watcher 状态、`problems`。
- 扩展侧：`ModuleConfigReadResult.problem` 上报到会话事件日志，UI 在子代理面板显示一次黄色提示（不打断）。
- 排查口诀：值不对 → 先看 `context-dump.json` 的来源层，再看 `ext-context.json` 的 `generated_at`。

## 8 `agents/config.json` 退役计划

| 版本 | 行为 |
|---|---|
| S3 | 投影上线；PF 仍写 `agents/config.json`（双写一版，给未升级扩展留活路） |
| S3+1 | 停写 `agents/config.json`，保留 `ensure_module_config` 只做「文件缺失时补一份」 |
| S4+1 | 读取兼容删除；文件仅在用户手编时被尊重（作为 legacy override），文档标注 deprecated |

退役判断标准：`ext-context.json` 上线后一个版本周期内，扩展日志中 `problem` 与 legacy fallback 命中为 0。
