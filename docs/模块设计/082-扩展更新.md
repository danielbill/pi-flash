# 082 - Pi 扩展更新检测与更新

## 背景

pi 的扩展（= pi package，settings.json `packages` 条目）更新频繁，PF 要能**检测**并**更新**它们。

职责对齐：

- **pi 本体升级 = PF 发版的事**（vendored 钉版，bump vendor + VERSION + pi-link 符合性测试，用户经 081 拿新版）。
- **扩展的检测与升级 = pi 生态的内建能力**（`pi update --extensions`）；PF 不自己发明版本判断。
- **PF 只做触发壳**：检测（registry/git 逐包探测）+ 执行（vendored pi CLI）+ 两处 UI。

## 为什么检测是 Rust 移植而不是 SDK/RPC

| 通道 | 结论 |
|---|---|
| RPC | 协议无任何更新相关方法（`docs/agents/pi-rpc.md` 方法面实测） |
| SDK | pi-web 的 `checkPluginUpdates` 是进程内 SDK，PF（Rust）吃不到 |
| CLI | `pi update` 无 `--check`/dry-run 旗标 |

pi 的 `DefaultPackageManager::checkForAvailableUpdates()`（`core/package-manager.d.ts`）证明**检测与执行是分离的**，但其输入（settings 多层 scope、dedupe、installedPath 解析）由 SDK 私有方法维护。PF 按 pi-web `lib/plugin-updates.ts` 的语义（四态、来源解析、逐包探测）用 Rust 实现，包清单直接读全局 settings.json 的 `packages`（扩展页 040 已有同源读取）。

## 检测（services/pi_extension_updates.rs + npm.rs）

检测零写入、不碰 node_modules。对全局 `packages` 逐条，四态（pi-web PluginUpdateState 同名）：

- **unsupported**：npm 钉精确版本（`npm:pkg@1.2.3`）/ git 钉 ref / 本地路径——无法自动检测
- **error**：未安装 / 网络失败 / `PI_OFFLINE=1` / 非标准布局读不到实装版本
- **npm 来源**：`<install>/package.json` 实装版本 vs registry 最新版——
  `ureq` GET `https://registry.npmjs.org/<name>`（scoped 名 `/` → `%2F`）取
  `dist-tags.latest`；来源带 `^` 等范围时 latest 命中则用、否则在 `versions`
  里取满足范围的最大值（maxSatisfying）；`beta`/`next` 等其它 dist-tag 直查
  `dist-tags.<want>`；semver `gt` 判定有新版。请求头
  `Accept: application/vnd.npm.install-v1+json`（裁剪文档，实测
  `pi-mcp-adapter` 全量 115 KB），超时 8s，base 可用 `PI_FLASH_NPM_REGISTRY`
  覆盖（私有镜像）
- **git 来源**：本地 `rev-parse HEAD` vs `ls-remote origin <upstream>`
  （先解析 `@{upstream}`，解析不到退 `HEAD`；`GIT_TERMINAL_PROMPT=0`、
  CREATE_NO_WINDOW；子进程 10s 超时强杀）
- 每包独立线程（`std::thread::scope`），结果顺序与清单一致
- 落盘路径复用 `pi_link::skills::package_install_dir`（npm=`~/.pi/agent/npm/node_modules/<pkg>`、git=`~/.pi/agent/git/<host>/<path>`）

### 边界与约束

- **`.npmrc` 不解析**：`registry=` 覆盖与私有 scope 鉴权直连读不到；私有源上的扩展落 `error`（可用 `PI_FLASH_NPM_REGISTRY` 指到镜像解决）。
- **`PI_OFFLINE=1`**：整轮不发请求，全部 `error`。
- **error 不进 UI**（定稿）：这只是升级检测，没检测成功对用户不重要，`error` 与 `up_to_date` 在界面上同为「无症状」——安静原则覆盖四态，新会话页与扩展页箭头只反映 `update_available`。
- **但失败要可诊断**：`PkgUpdateResult.detail` 记失败原因（registry 不可达 / 本地 package.json 读不到 / 无 dist-tag…），仅在开发构建（`cfg!(debug_assertions)`）打 `[ext-updates] error <source>: <detail>` 到 stderr，release 静默。历史教训（首版经 `npm view` 子进程探测，release 布局不带 `node_modules/npm` 时整条链静默失效）沉淀为这条不变量：失败不能连开发者都看不见。
- 只查**全局** scope（与扩展页 global only 对齐；项目级 `.pi/settings.json` 不查）
- 更新动作不区分 up-to-date/unsupported 包——pi 自己会跳过无可更的包
- `pi update` 默认 target 是 **self（更新 pi 本体）**，PF 永远不裸跑不带旗标的 update（vendored 钉版红线）

## 执行

复用扩展页 040 的 CLI op 管道（`mc_cli_op` 后台线程跑 vendored pi CLI + op 泵收尾刷新；实现住 `settings/custom_models/mod.rs`）：

- 全部：`update --extensions`
- 单包：`update --extension <source>`（**注意 `--extension` 与 `--extensions` 解析期互斥**，单给 `--extension` 即扩展目标）
- 完成消息提示「重启会话后生效」（扩展在侧车启动时加载）；op 泵收尾时重跑检测刷新箭头

## UI（两处提示）

1. **新会话页**（`session/new_session.rs`）：选择项目栏下方通知块——零高锚点 + 卡片（宽 = 内容列 80%，标题行下分隔线，列表上限 300px 超长滚动）：可更新列表（名字 + ↑）+ 标题行右侧【更新全部(n)】（与扩展页同款 `config_button`）。安静原则：检查中不显示、n=0 不渲染。
2. **设置·扩展页**（`settings/pi_extensions/`）：
   - 列表宽 `widgets::LIST_W`（450，模型/技能/MCP/子代理页共享）
   - 有更新的行标签右侧 ↑
   - 列表 title 行【更新全部(n)】：恒渲染，无可更新或任一 op 进行中禁用灰态；更新全部进行中显示「更新中…」
   - 详情 panel 删除 icon 左侧【更新】按钮：仅该包检测为「有可用更新」（或正在更新本包）时显示；更新本包显示「更新中…」禁用，任一 op 进行中禁用

## 状态与数据流

```
启动揭幕后延迟加载（shell/chat/boot.rs）→ Chat::spawn_pi_extension_updates_check
  → 后台 check_all() → aux.pi_extension_updates { results, checking }
      ↑ op 泵收尾（装/卸/更后）也重跑
新会话页 notice / 设置页箭头与按钮 ← 只读 aux.pi_extension_updates
点击更新 → PkgOp::Update(Some|None) → mc_cli_op → op 泵清零 + 刷新 + 重检
```

## v2 混排 PF 插件更新（2026-11-28）

新会话页通知卡扩展为「pi 扩展 + PF 插件」**混排一张卡**（标题【扩展更新】，键
`new_session.extension_updates`），用户定稿三点：

- **PF 行恒排末尾**：pi 行在前（顺序 = settings.json 清单序），PF 行追加其后；
- **PF 行带前缀**：`Pi-Flash · 会话上下文自动压缩`（前缀产品名三语同形，硬编码
  `PF_ROW_TAG` 不进 i18n；显示名取索引 zh 名，空则包名）；
- **【更新全部(n)】一并更新**：n = 两侧之和；点击先 PF 批量、队列耗尽后接 pi CLI
  `update --extensions`（跨管线串行）。设置·扩展页按钮保持 pi-only 不变。

### 检测与加载（零阻塞红线）

PF 更新判定 = [`pf_updatable_entry`]：台账版本 < 索引版本 **且** 新版 `min_pf`
满足（082 v2 复核定稿 2026-11-28：提示算法不只比版本号——插件新版要求的 PF
版本须 ≤ 当前 PF，要求了装不上的版本 = 白提示；混排卡行、市场卡与已装页
↑/更新钮同源此谓词）。含停用包。pf_scan 是 N+2 串行 HTTP（比 082 检测稍慢），因此：

- 预取挂 **splash-gate 延迟泵**（`pumps.rs`，082 调用之后）：揭幕后才触发、后台
  线程、完成才 notify 追加 PF 行——绝不阻塞启动与新会话页首帧；索引未到时卡片
  先按 pi 行渲染；
- 失败安静（debug stderr），索引缺位 = PF 行静默缺席（安静原则同 082）；
- 行数据沉缓存（`aux.pi_extension_updates.pf_rows`），渲染路径零磁盘（market.md
  陷阱：渲染每帧禁重活）；PF 装/更/卸完成闭包与市场进页扫描完成后刷新。

### 执行（跨管线批量）

- PF 阶段：链条挂 `pf_install` **完成闭包**推进（pending 单飞使顺序循环调
  `pf_update` 会全部静默 no-op）——`PfState.update_queue` + `mixed_batch`；
  失败不堵队（Err 也弹下一家，原因落市场页既有错误行）；
- **min_pf 拒载在设 pending 之前 return，不触发完成闭包**——提示层已按
  `pf_updatable_entry` 滤掉拒载包（行都出不来），播种再按 `min_pf_satisfied`
  预过滤兜底防卡死；链条推进时还逐个复核（防批量中途市场页重扫换表竞态）；
- pi 阶段：队列耗尽清位后，`available()>0` 才发 CLI 更新（op 泵收尾自动重检 082）；
- 卡片按钮「更新中…」/禁用判定覆盖两管线：`pkg_op.is_some() || mixed_batch ||
  pending.is_some()`。

### 边界

- 停用包照出行、更新后台账回 enabled = 市场已装页现有单更行为，批量不特殊处理；
- 混排批量中用户在设置·扩展页手动点【更新全部】：`mc_update_all_packages` 的
  `pkg_op` 守卫天然防重（PI 阶段已发 op 时批量收尾的 pi 调用静默跳过）；
- min_pf 拒载的新版**静默不提示**（提示层已滤）：插件照常用当前版，「升级 PF 后
  再更」不经此卡表达（stale 需更新标签 / need_newer_pf 错误行仍在市场页）。

## 升级复核

pi CLI 旗标语义以 `package-manager-cli.js` 的 `parsePackageCommand` 为准；vendor bump 时复核 `--extensions`/`--extension` 互斥关系与默认 target（现为 self）。
