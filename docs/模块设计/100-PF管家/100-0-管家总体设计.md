# 100-0 管家总体设计

> 状态：设计定稿（2026-11-04 讨论沉淀）
> 定位：PF 核心器官。深度耦合、有界面、有设置、不可卸载。

## 0. 定位与宪法

1、管家是 PF 从 Harness 变成 Agent 的分界线：
- 无管家 = Harness：工具箱 + 会话管理，被动响应，会话之间是孤岛
- 有管家 = Agent：常驻身份、全局感知、主动行动权，知道自己家几间房在亮灯
2、管家本体不可插拔；管家的能力是可插拔的（插件）
3、宪法一句话：PF 只回答"发生了什么、去哪看"；管家能力插件决定"这对我意味着什么、该做什么"
4、推论：PF 代码里不允许出现任何管家业务代码（提取会话内容、判定第一轮是否该命名等均不属于 PF）

## 1. 架构分层

```
┌────────────────────────────────────────────────┐
│ 普通会话（微信 / 桌面端 / web）                    │
│  出厂标配工具：ask_butler()                       │
└──────────────┬─────────────────────────────────┘
               │ 查询 / 事件（走 daemon）
┌──────────────▼─────────────────────────────────┐
│ 管家（PF 核心子系统，与 daemon 深度绑定）           │
│  ┌────────────────┐  ┌───────────────────────┐ │
│  │ 管家服务（无LLM） │  │ 管家大脑（LLM会话）      │ │
│  │ 全局注册表/心跳   │  │ 能力插件:Rename/Diary… │ │
│  │ 事件路由/动作网关 │  │ manifest+prompt 可插拔 │ │
│  │ 状态查询应答     │  │ 被服务唤醒时才运行       │ │
│  └────────────────┘  └───────────────────────┘ │
└────────────────────────────────────────────────┘
```

1、管家服务：常驻 daemon 进程内（决策：同进程模块，不做独立进程），无模型、永远在线，崩溃风险低
2、管家大脑：daemon 监督的 headless 系统会话；崩了服务自动拉起；不在注册表中与普通会话并列展示（标记 system 身份）
3、普通会话永远只接触服务，不接触大脑

## 2. 双路径

### 2.1 查询路径（跨会话状态）

1、任何会话、任何渠道，调用 `ask_butler("status")`
2、管家服务直接从注册表 + 心跳应答，内存数据、毫秒级、不过 LLM（注册表数据是确定性的）
3、全渠道对称：微信里问桌面端状况，与桌面端本地问，视图一致
4、注册表数据结构从第一天起为"被查询"设计，不只是为事件分发

### 2.2 事件路径（主动能力）

1、PF/daemon 发事件 → 服务按订阅声明过滤 → 入队 → 唤醒大脑
2、大脑按插件 prompt 干活 → 产出动作 → 服务动作网关回写

## 3. 会话感知（SessionRegistry）

### 3.1 为何注册表必须在 PF 层

1、pi 扩展钩子（session_start / session_shutdown / turn_end / session_info_changed 等）是**进程内自知**的，只能回答"我自己这个会话"，pi 内核没有全局会话管理器
2、PF 是壳，所有会话由它拉起（SDK createAgentSession / RPC 子进程），父进程天然知道 spawn/exit
3、结论：注册表 primary source = PF 层；pi 扩展只做心跳补充，不是感知主体

### 3.2 四路数据源

| 来源 | 提供什么 | 弥补什么 |
|------|---------|---------|
| PF spawn/exit 事件 | 注册/注销 entry（权威） | 谁存在 |
| pi 全局扩展心跳（session_start/turn_end touch） | lastActivity + 崩溃兜底 | entry 尸体（进程崩了没 unregister） |
| 现有 pi-web-session-index.json | 静态元数据（首条消息、消息数） | 不重复造 |
| PID 探活 | 进程级真伪 | 区分"活着"和"还热乎" |

全局扩展装 ~/.pi/agent/extensions，对所有 pi 进程生效，覆盖绕过 PF 的 standalone CLI 会话，标记 origin: standalone；PF 托管的标记 origin: pf；按 sessionId 去重合并。

### 3.3 状态机

```
streaming  → turn 进行中
idle       → 进程活着，N 分钟无活动
orphan     → 注册表有 entry，PID 已死（崩溃残留）
ghost      → 有 pi 进程，无 entry（扩展未装/未上报）
```

### 3.4 Entry 数据模型

```
sessionId / pid / cwd(project) / channel(wechat|desktop|web|cli)
origin(pf|standalone) / status / model·provider
startedAt / lastActivityAt / firstMessage / messageCount / pinned
```

## 4. 事件协议（瘦事件）

1、事件 = envelope + 引用，**不含会话内容**（PF 零业务代码的保证）
2、PF 无脑广播通用事件（session.turn_end 带 turnNumber、isFork 等通用字段），不理解事件含义
3、订阅声明（事件类型 + 字段谓词，如 `turnNumber == 1 && !isFork`）注册到 daemon，**入队前过滤**；谓词是声明式配置，不算业务代码
4、turnNumber 语义 = 首次成功完成的 assistant run，裸计数会踩 fork/重试的坑
5、投递语义：
- 管家忙 → 事件进 daemon 队列（持久化），空闲时 drain 全队列批量处理
- eventId 幂等，防重放
- 事件带 TTL：积压超时（如 1h）走降级路径，不再打扰大脑

```jsonc
{
  "eventId": "evt_...",
  "type": "session.turn_end",
  "sessionId": "01a1a...",
  "turnNumber": 1,
  "isFork": false,
  "cwd": "...", "channel": "wechat",
  "detailRef": "pf://session/01a1a.../turns/1"   // 想深看时的引用
}
```

## 5. 能力插件契约

```yaml
id: rename-first-turn
version: 0.1.0
subscriptions:
  - event: session.turn_end
    where: turnNumber == 1 && !isFork
tools: [read_session, rename_session]   # 声明所需端口
settings:                               # 贡献给管家设置界面自动渲染
  style: { type: string, default: "简洁" }
permissions: { read: any-session, write: rename-only }
prompt: |
  根据会话首轮内容生成会话名……
```

1、能力 = manifest + prompt（数据），不是代码；丢文件进目录即生效
2、插件声明式订阅；daemon 按声明分发
3、插件读取会话走通用读取工具（read_session），支持通用分页/截断参数（limit/offset/maxChars）——通用参数，非业务定制
4、动作回写走服务动作网关：插件产出动作 → daemon 校验 → 应用到目标会话 → 触发 pi 原生 session_info_changed，UI 自动刷新
5、首个官方插件：rename-first-turn（从出生示范"能力应该是插件"）

## 6. Rename 完整链路（首个场景）

```
新会话 S 第 1 轮结束（首个成功 assistant run）
 → PF 发 session.turn_end(turnNumber=1)
 → 服务按订阅声明匹配 rename 插件 → 入队 → 唤醒大脑
 → 大脑 read_session 拉首轮内容 → 生成会话名
 → rename_session(id, name) → daemon 校验 → 目标会话改名
 → session_info_changed 广播 → registry 更新 → UI 刷新
```

降级：命名事件积压超 TTL → 直接用 firstMessage 前 20 字符确定性命名，不阻塞。
用户已手动改名 → 尊重用户，跳过（registry 记 renamedBy=user）。

## 7. 界面与设置

1、权限模型：
- 读取范围：按项目 / 按渠道 / 按隐私级别控制管家可看哪些会话
- 动作审批：rename 免审批；未来重动作（关会话、发消息）可设"询问后执行"
- 作用域：插件按项目生效或全局生效
2、插件贡献设置：manifest.settings 声明，管家设置界面自动渲染，插件不自造界面（对标 VSCode contributes.configuration）
3、活动日志：管家消费了哪个事件、跑了哪个插件、做了什么、为什么——全落日志并界面可视化；用户对自主行动实体的信任建立在此
4、管家设置页：插件管理 / 权限 / 日志

## 10. 决策记录

1、瘦事件而非胖事件：PF 零业务代码；定制化从 PF 源码搬家到插件（数据）
2、管家 = 核心器官（不可插拔）；能力 = 插件（可插拔）
3、查询走服务不过 LLM：状态是确定性数据
4、第一轮判定规则归插件订阅过滤，不归 PF
5、管家服务与 daemon 同进程，不做独立进程
6、管家的查询路径与事件路径分离：查询要秒回，事件才需要智能
