# 扩展装载与工具声明模型（034）

> 实现落点：`crates/app/src/session/runtime/spawn.rs`（spawn 参数装配收口）、
> `crates/app/src/session/tools_recipe.rs`（`full` / 自定义配方）、
> `crates/app/assets/full_activate.ts`（激活器，编译进二进制）、
> `crates/pi-link/src/extensions.rs`（pi 发现口径复刻）。

## 1. 现状确认

spawn 参数收口在 `session/runtime/spawn.rs::SessionRuntime::spawn`
（`pi_link::client::spawn` 落地，vendored pi `--mode rpc`）。工具预设
`tools_preset` 只切**声明轴**（`--tools` / `--no-tools`），扩展装载轴由
`-ne` + 显式 `-e` 精确集控制：

| 档（`tools_preset`） | 装载轴 | 声明轴 |
|---|---|---|
| `chat-only` | 全装 | `--no-tools`（0） |
| `read-only` | 全装 | `--tools read,grep,find,ls,present_plan` |
| `default` | 全装 | `--tools read,bash,edit,write[,pfctx_manager],present_plan` |
| `full` | **精确集**（个人扩展 + 内置扩展，包一个不装） | `--tools bash,read,edit,write,grep,find,ls[,agent][,pfctx_manager],present_plan` |
| `custom`（**默认档**，菜单名「自定义」） | **会话扩展集**（唯一装包的档） | 不发 `--tools`——full_activate.ts 把 active 收敛为「full 7 件 ∪ pi 自己激活的」 |

- `configured` 档已移除（`tools_preset` 默认 `custom`）；`settings.defaultTools`
  不再驱动 app 的档位，只在自定义档里仍决定 `+codemode` 之类的 pi 侧激活。
- `present_plan`（031-1 计划模式）、`agent`（045 子代理，模块开关开着才点名）、
  `pfctx_manager`（001-4 自我调试开着才点名）必须显式点名——`--tools` 是
  **注册级硬 allowlist**：不点名的扩展/内置工具连注册都进不去
  （031 A–H 组实测），唯一能带出扩展工具的组合是「不发 `--tools` +
  扩展 `setActiveTools`」（custom 档）。
- 全档位恒定追加：`--exclude-tools acp_delegate,acp_delegate_wait,acp_delegate_cancel`
  （外部委派面与 PF 的 `agent` 撞车，denylist 对扩展工具同样生效）；计划模式
  扩展与任务会话标记扩展各 `-e` 一条。
- **会话级扩展清单（session-ext.json）全档位统一消费**（spawn 前按注册状态
  过滤 + 版本换代自愈回写）——此前只有 custom 档读它，插件 ext 在其它档下
  永远挂不上。

`-ne` 只关扩展（发现 + 配置 + **内置**）；skills / prompts / themes 各有自己的
开关（`-ns` / `-np` / `--no-themes`），个人 skills 在任何档照常可用。

设置·扩展页的启停是**全局**语义：往 settings.json 里把该扩展写成
`{source, extensions:[], skills:[], prompts:[], themes:[]}`（pi 认这个「资源置空」
过滤）。它改不了单个会话。

### 1.1 `full` 档语义：不装载，而不是「装载 + 掐工具」

早期 full 只发 `--tools`：探针实测扩展照样全装（命令集与 configured 一字不差）、
注入照来、只有工具被 allowlist 挡掉——这正是 36KB 提示词注入的来源。现行
full 改走「精确集」结构性路线（配方与理由见 §1.3）：`-ne` 关掉发现/配置/内置
扩展，包一个不装，注入从源头消失；个人扩展与内置扩展显式 `-e` 加回。

### 1.2 核心约束：扩展提示词注入与工具声明会不一致（嘴手一致规则）

会话文件回放证实（`role:"system"` 的 `sections` 按序回放）：

| 会话 | 声明工具 | 系统提示词总字符 | 其中 `agent_browser` 注入 |
|---|---|---|---|
| 只发 `--tools` 的档 | 7（bash,read,write,find,ls,edit,grep） | 53,589 | **36,417 字符 = 67%** |
| custom 冒烟（只选 pi-web-access） | 12（7 内置+codemode+4 web） | 17,628 | **0**（扩展没装载 → 没注入） |

机制：

- 扩展注入是**独立的命名 section**（`sections.agent_browser`，由
  `agent-browser/index.js` 拼 `PROJECT_RULE_PROMPT` + guidelines），**与工具注册
  完全解耦**；
- pi 自己的 core section 会按 allowlist 自适应，**扩展却感知不到自己的工具被掐**；
- 工具带 `namespace{name, description, instructions}`，命令带
  `sourceInfo{path,origin,baseDir}` → 工具/注入 ↔ 扩展身份的映射材料是现成的。

**违反面**：扩展全装 + 工具全掐的档全部违反；最极端时 0 个可用工具，系统提示词
里却有 36KB「优先使用原生 agent_browser 工具」。危害不止浪费上下文：模型会去
调用**不存在的工具**（幻觉 tool call / 报错 / 绕路 bash）。

**规则（档位设计必须满足）**：*系统提示词里推荐的工具，模型必须真的能调用*
（`注入 ⊆ 声明`）。两条满足路径：

1. **收窄装载** —— 不装该扩展则无注入（custom / full 天然满足，冒烟 0 注入）；
2. **装载但抑制注入** —— 不可靠：pi 的扩展加载顺序是
   `mergePaths(cliEnabledExtensions, enabledExtensions)`，CLI `-e` 排在扩展
   前面，抑制器先跑、扩展的 `before_agent_start` 后跑并写回（agent-browser
   就是这么注入的），`-e` 无法排到扩展后面（论证见 §1.3）。

## 2. pi 提供的粒度开关（可用的杠杆）

| 杠杆 | 粒度 | 说明 |
|---|---|---|
| `-e/--extension <路径\|扩展>` | 扩展（文件/目录/扩展） | 扩展 = 该扩展全部资源；文件 = 单个扩展 |
| `--skill <路径>` | 单个 skill（目录/SKILL.md） | 与 `-ne -ns -np --no-themes` 组合可只留点名资源 |
| `--prompt-template <路径>` | 单个提示词模板 | repeatable |
| `--theme <路径>` | 单个主题 | **主题不在 `get_commands` 里**，库存要另找 |
| `-ne / -ns / -np / --no-themes / -nc` | 全局隔离 | 关掉「发现 + 配置」的那一类资源，显式路径参数仍然生效 |
| 扩展 `setActiveTools(名单)` | **进模型的工具集** | 扩展可全注册而 active 精确等于点名集合（custom 档 full_activate.ts 即此机制） |
| settings 资源数组（`!`/`+`/`-` glob） | 仅 settings 作用域 | 用户级相对 agent dir、项目级相对 `.pi`；不能当会话参数用 |

**库存来源**：活进程 `get_commands` 每条带 `source`（`extension`/`prompt`/`skill`）与
`sourceInfo{ path, scope, origin: "top-level"|"package", baseDir }` —— 等于 pi 自己
把「装了哪些资源、各自属于哪个扩展」报出来，不需要复刻 pi 的发现规则（npm/git/本地扩展的
约定目录、manifest 过滤、glob 取反…）。`pi list` 另外给出每个扩展的安装路径。
缺口只有一个：**主题没有对应的命令，拿不到 path**。

## 3. 设计空间（四层，正交）

```
① 资源装载   装哪些扩展 / skills / 提示词 / 主题        （扩展级 → 资源级别）
② 工具声明   哪些工具写进模型上下文（active）            （被 --tools 一刀切 / custom 由 full_activate 收敛）
③ 作用域     会话 / 项目 / 全局默认 + 持久化
④ UI 信息    选了之后到底会发生什么（工具数、资源计数、provider）
```

现状：

- ①：custom 档已能按会话选**扩展**（含 PF 插件挂载通道）；资源级别（每扩展 ×
  四类，或单文件）尚无。
- ②：带 `--tools` 的档按名单声明；custom 档不发 `--tools`，由 full_activate.ts
  把 active 收敛为「full 7 件 ∪ pi 自己激活的 ∪ transcript 重挂恢复」（§1.4）。
- ③：`tools_preset` 不落盘，重启回落默认档（custom）；`ext_sources` 每个会话
  落 session-ext.json，跨重启恢复。
- ④：勾选菜单已有 token 标注、项目小标、勾选计数；资源计数 / provider 未显示。

## 4. 推荐路线（S1 已落地；S2/S3 未实现）

### S1（已落地）会话级**扩展**选择 = 自定义档
`-ne -e <会话选中扩展…> -e builtin:<settings 里开着的> -e full_activate.ts`，
不发 `--tools`。`full_activate` = full 内置 7 件 ∪ `getActiveTools()`（保留 pi
自己激活的 deferred/codemode 语义）。见 `session/tools_recipe.rs`。

**源消重（managed npm 路径）**：清单里的 `npm:x` 拼装前先换成
managed 安装路径（`~/.pi/agent/npm/node_modules/<pkg>`，user 根优先、项目根
`<cwd>/.pi/npm` 兜底；`pi_link::extensions::managed_npm_source_path`）。原样发
`-e npm:x` 会让 pi 按 temporary scope 又装一份到 `~/.pi/agent/tmp/extensions`
（0700 私有临时安装）——同一插件 managed 根 / tmp 双份 node_modules + 版本漂移；
本地路径源走 `resolveLocalExtensionSource` → `collectPackageResources` 全套
挂载（extensions+skills+prompts+themes），零复制零临时安装。未安装/装坏的源
原样回退 `-e npm:x`，由 pi 临时安装兼做兜底。

**内置扩展两条实测约束**（`tools_recipe.rs` 模块注释同款口径）：
- `-ne` 关的是「已配置 + 发现 + **内置**」扩展：`builtin:codemode`、
  `builtin:tool-search` 一起消失，所以要按
  `pi_link::config::enabled_builtin_extensions` 逐条 `-e` 加回；
- `-e builtin:<name>` 会**覆盖** settings 里的 `-builtin:<name>`，所以内置清单
  必须跟着 settings 走，不能无条件写死（否则用户关掉的 MCP 会被强行打开）。

### 1.3 为什么 `full` 走「不装载」而不是「装载 + 抑制注入」

pi 的扩展加载顺序（vendored pi）：

```js
extensionPaths = this.noExtensions ? cliEnabledExtensions
                                   : this.mergePaths(cliEnabledExtensions, enabledExtensions)
// mergePaths(primary, additional) = [...primary, ...additional]
```

⇒ **CLI `-e` 排在扩展前面**；`before_agent_start` 的 handler 按扩展加载顺序跑 ⇒ 我们的
`-e` 抑制器**先跑**，扩展后跑并写回（agent-browser 就是这么注入的：
`event.systemPromptOptions.sections.agent_browser = fullInstructions(ctx)`）。`-e` 又
没法排到扩展后面，所以「装载 + 抑制」在 `full` 上不可靠（`forceSystemPrompt` 能让模型
拿不到，但 transcript 仍记录 sections ⇒ 面板照样显示 36KB，语义更绕）。

**`full` 档设计**：`full` = `-ne`（扩展一个不装）+ 显式 `-e` 加回**个人扩展**
（`<agent dir>/extensions/*` 与 settings `extensions` 数组里的普通路径，如
pi-notify）+ `-e builtin:<settings 里开着的>` + `--tools <full 名单>`。
结构性零扩展注入；个人扩展不受影响；skills / prompts / themes 本来就不受
`-ne` 管辖（个人 skills 照常）。
代价：`full` 档没有扩展的命令 / provider / MCP（freeflow 模型要在「自定义」里选）。

实现：`pi_link::extensions::personal_extensions()`（复刻 pi 发现口径：顶层
`*.ts`/`*.js`、一级子目录的 `pi.extensions[]` / `index.ts` / `index.js`，
**不递归**；项目作用域发现受 project trust 约束，交给 pi 自己的信任流程）+
`tools_recipe::full_args`。

### 1.4 重挂工具恢复

custom 档「每轮可调」的重绑语义在 pi ≥0.86 有个隐藏交互：resume 且未发
`--tools` 时，pi 按 transcript 工具账本（system 消息的
`toolsAdded`/`toolsRemoved`）恢复 active 集——中途卸载过的扩展重挂后，其工具
「出现过 → 不算新工具、又被回放移除」→ **注册但永不激活**（pi-mcp-adapter /
pi-web-access 同症；扩展侧无法自救）。`full_activate.ts` 在 `session_start`
把「transcript 声明过（toolsAdded 出现过）+ 本进程已注册 +
exposure=direct + 尚未激活」的工具并回（即 pi 本会给它们的默认态；
收敛性论证见脚本头注释与 `test/041/重挂工具恢复/`；陷阱详录
`docs/agents/pi-rpc.md`）。

`full_activate.ts` 的落盘与解析（`tools_recipe::activate_script_path`）：
`PI_FLASH_FULL_ACTIVATE` 显式覆盖 → 开发工作区
`crates/app/assets/full_activate.ts`（编译期路径，改完即生效）→
内容落 `~/.pi-flash/full_activate.ts`（release 包不带 assets/ 目录）。
按 `-e` 顺序恒排最后，跑在所有包扩展的 `session_start` 之后。

## 6. 档位与持久化设计

| 项 | 设计 | 实现 |
|---|---|---|
| 档位表 | 无 `configured`；`full` 之下有**自定义**，且**默认档 = 自定义** | 菜单行 + `tools_preset` 默认 `custom`（`runtime.rs`） |
| `full` | **禁止任何扩展注入**（不是限制 extensions：个人扩展照常） | `-ne` + personal + builtins + `--tools`（结构性零注入，§1.3） |
| 自定义 | full 精确集 + 本会话扩展清单 | `tools_recipe::full_plugin_args` |
| 对话中途 | **允许调整**：勾选即生效，下一轮发送前统一重绑（连点 N 项只重绑一次，运行中不掐轮）；入口仅自定义档激活 | `pi_extension_picker` + `pending_ext_sources`（046 任务页嵌入态写任务表单） |
| 持久化 | **每个对话保存一份清单**，重启恢复 | `~/.pi-flash/session-ext.json`（`pi_link::session_ext`）；草稿→会话文件迁移在 `on_file_bound`；删会话清条目（`session_clean`） |
| 其余三档 | `chat-only` / `read-only` / `default` 只发 `--tools`（名单含 present_plan；read-only/default/full 按开关点名 `agent` / `pfctx_manager`） | `spawn.rs` |

（注：默认档取自定义后，`settings.defaultTools` 不再驱动 app 的档位；它在「自定义」档
里仍决定 `+codemode` 之类的 pi 侧激活。）
