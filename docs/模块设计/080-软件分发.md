模块代码：distribution
原始调研：`docs/INSTALL_UPDATE.md`（先例数据、方案对比全文、资料出处；本文是定稿设计，冲突以本文为准）

## 0. 目标与边界

**目标**：用户一条命令完成**首次安装**，以后**更新也是同一条命令**，与 pi-web 心智逐字一致：

```bash
npm install -g pi-flash@latest   # 没装 = 首次安装；装过 = 更新
pi-flash                          # 启动
npm uninstall -g pi-flash         # 卸载（载荷在包目录内，一并清除）
npx pi-flash@latest               # 不常驻安装直接跑
```

**边界（本期做）**：

- ✅ 方案 A：npm 薄壳包（`npm/` 目录）+ 载荷走 GitHub Releases 下载
- ✅ release.sh 裁 esbuild + 上传 Release 资产/SHA256SUMS（P0，一切下载方案的前提）
- ✅ 版本三处（`crates/app/Cargo.toml` / git tag / `npm/package.json`）收敛进 release.sh 单点改写

**非目标（本期不做，留作增量）**：

- ❌ 应用内自动更新（对应 PORT_PLAN M6，P2 再做；复用薄壳下载器）
- ❌ PowerShell/curl 安装脚本、winget、brew——照顾**无 Node 用户**的后续通道，不阻塞主线
- ❌ `cargo install`：vendored gpui + `[patch.crates-io]` + 分钟级编译，排除

**用户侧门槛**：机器有 Node ≥ 22.19（pi / pi-web 用户群本就有；沿用 pi-web `node-version.js` 的校验写法）。

## 1. 决策依据（调研摘要，全文见 `docs/INSTALL_UPDATE.md`）

### 1.1 pi-web 为什么能做到

npm registry 自带 install / update / uninstall / rollback / 缓存 / 镜像全套语义，
pi-web 只是把预构建 `.next` 产物直接塞进 tarball（实测 `unpackedSize` 33.5MB / 740 文件）。
**"一条命令"是 npm 给的，不是私有机制。**

### 1.2 PF 载荷实测（2026-10-10）

| 组成 | 解压 | 说明 |
|---|---|---|
| `pi-flash.exe` | 70 MB | release 构建 |
| `node.exe` | 93 MB | 内置 node（铁律：不读 PATH/系统 node） |
| `vendor/pi` | 416 MB | **其中 284MB 是 `@esbuild/*` 的 26 个平台二进制，只用得到 1 个** |
| 合计 | ≈580 MB | tar+gzip 整包实测 **138 MB** |

- 裁 esbuild 后：解压 ≈310 MB、下载压缩包 **≈120 MB**（与方案解耦，任何方案都先做）
- GitHub Releases 现状：**从未上传过资产**（`gh release list` 为空）
- npm 包名 `pi-flash`：**未被占用**（P1 落地前先 `npm publish` 0.0.1 占位防抢注）

### 1.3 为什么选方案 A（薄壳 + GitHub Releases）而非全进 tarball

| | 方案 A（选定） | 方案 B 全进 tarball | 方案 C 安装脚本 |
|---|---|---|---|
| 一条命令装+更 | ✅ npm 语义 | ✅ npm 语义 | ⚠️ 重跑脚本/应用内提示 |
| 需要 Node | ✅ 需要（pi-web 同款） | ✅ 需要 | ❌ 不需要 |
| publish 风险 | 薄壳几 KB，无风险 | ~150-200MB base64 上传，易超时；npmmirror 大包同步慢；回滚保留旧大包撑 packument（drizzle 曾踩 100MB 上限） | — |
| 载荷通道 | GitHub Releases（Azure CDN） | npm 镜像（国内反而快） | GitHub Releases |
| 卸载/回滚/版本管理 | npm 免费 | npm 免费 | 全部自己写 |

先例：electron（主包 1.17MB，postinstall 下 zip）、`@openai/codex`（Rust，主包 13KB + 平台载荷包）、`@biomejs/biome`（Rust，optionalDependencies 平台子包）、playwright/puppeteer（postinstall 下浏览器）。
**Rust 程序走 npm 是业界常态：npm 只当"带版本管理的下载器"，exe 本体不认识 npm。**

## 2. 包结构（`npm/` 目录入库，随 release 发布）

```
npm/
├── package.json          # name: pi-flash, version: = Cargo 版本（release.sh 同步）
│                         # bin: { pi-flash: bin/pi-flash.js }
│                         # scripts: { postinstall: "node bin/fetch-payload.js" }
│                         # engines: { node: ">=22.19.0" }
├── bin/
│   ├── pi-flash.js       # 启动器（见 §3.1）
│   ├── fetch-payload.js  # 下载器 CLI 入口（postinstall 调用；见 §3.2）
│   └── lib.js            # 共享逻辑（探测/下载/校验/解压/落位）
├── test/
│   └── e2e.js            # 本地回环端到端自测（node npm/test/e2e.js，19 项断言）
└── README.md
```

### 3.1 启动器 `bin/pi-flash.js`

1. Node 版本检查（复用 pi-web `node-version.js` 写法，低于 22.19 友好报错退出）
2. **自愈检查**：`payload/.payload-version === package.json.version`？
   - 否/缺失 → 调同一份下载逻辑补齐（兜底 `--ignore-scripts`、镜像剥 postinstall、半途断网）
   - 是 → `spawn(payload/pi-flash.exe)`，转发信号、透传退出码
3. 更新时旧实例运行导致目录锁（EBUSY）→ 提示"请先退出正在运行的 pi-flash 再执行"（pi-web README 同款文案）

### 3.2 下载器 `bin/fetch-payload.js`

1. **平台探测**：`process.platform` + `process.arch` → `win32-x64` / `darwin-arm64`（暂无资产的平台明确报错，不瞎猜）
2. **下载源**：`https://github.com/danielbill/pi-flash/releases/download/v<ver>/pi-flash-<ver>-<platform>.zip`；
   环境变量 `PI_FLASH_MIRROR` 可整体覆盖（国内镜像/自建回退口）
3. **校验**：取用顺序 `<资产>.sha256`（平台 sidecar，CI/release.sh 双方生成、互不覆盖）
   → `SHA256SUMS`（release.sh 生成，仅 Windows 包）。比对不过即删下载文件、退出非零
   （让 npm 报错，不装半截）；两个文件都找不到对应行也报错并给 release 页链接。
   sidecar 单列的原因：macOS CI 与本地 release.sh 都写 `SHA256SUMS` 会互相覆盖，
   sidecar 按资产名隔离，天然不撞车。
4. **原子落位**：解压到 `payload.tmp-<pid>` → rename 为 `payload/` → 最后写 `.payload-version`
   （崩溃自愈靠"无版本戳 = 重下"）
5. 下载失败自动重试（有限次 + 退避）；支持 Range 断点由 P2 优化，本期不做

## 4. 发布流水线改造（`scripts/release.sh` 追加）

```bash
# ① 裁非宿主平台 esbuild（Windows 包留 win32-x64；macOS CI 同理留 darwin-arm64）
ESBUILD_DIR="dist/pi-flash/vendor/pi/node_modules/@earendil-works/pi-coding-agent/node_modules/@esbuild"
for d in "$ESBUILD_DIR"/*; do [[ "$(basename "$d")" == "win32-x64" ]] || rm -rf "$d"; done

# ② 生成 SHA256SUMS + 上传 Release 资产（现状：从未上传过）
(cd dist && sha256sum "$ZIP_NAME" > SHA256SUMS)
gh release create "v$VERSION" --verify-tag --title "v$VERSION" \
  --notes-file "$NOTES_FILE" "dist/$ZIP_NAME" "dist/SHA256SUMS"

# ③ npm 版本对齐 + 发布（三处版本单点同步，禁止手改两处）
npm version "$VERSION" --no-git-tag-version --prefix npm
(cd npm && npm publish --access public)     # NPM_TOKEN 进 repo secrets
```

- macOS workflow 产的 zip + SHA256 同样挂到该 tag 的 release（资产名带版本与平台，薄壳靠它解析）
- 顺序：烟测通过 → 裁剪 → 打资产 → npm publish；任一步失败即中止，不发半套

## 5. 分阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** | release.sh 裁 esbuild + 上传 Release 资产（SHA256SUMS） | release 页可见 zip 与校验文件；下载解压烟测通过；pi-link 符合性测试通过；真机走一遍依赖 esbuild 的插件路径 |
| **P1** | `npm/` 薄壳包（下载器 + 启动器 + 自愈）；接进 release.sh；npm 0.0.1 占位 | 全新机器 `npm i -g pi-flash@latest && pi-flash` 可用；再发一版，**重跑同一条命令完成更新**；`npm uninstall` 清干净；`npm i --ignore-scripts` 后首启自愈成功；`npm i pi-flash@旧版` 回滚成功 |
| **P2** | 应用内检查更新（`npm view pi-flash version` 或 GitHub `/releases/latest`），提示后走同一下载器后台更新、重启生效 | 旧版启动收到提示；重启后版本号变化 |

## 6. 风险与预案

| 风险 | 预案 |
|---|---|
| Windows Node 装在 `Program Files`，`npm i -g` 要管理员权限 | 文档标注 + 提示 `npm config set prefix` 或提权；后续通道（安装脚本/winget）给无 Node 用户 |
| `--ignore-scripts` / 镜像剥 postinstall | 启动器首启自愈（§3.1-2），双保险 |
| GitHub Releases 国内慢/失败 | 重试 + `PI_FLASH_MIRROR` 回退；必要时默认候选列表加镜像 |
| 载荷传输损坏/被篡改 | SHA256SUMS 不符即失败重下 |
| 更新时旧 exe 运行锁目录 | 捕获 EBUSY → 提示先退出实例 |
| SmartScreen/杀软报警 | 与安装方式正交的存量问题；长期解 = 代码签名，单列技术债 |
| 裁 esbuild 后运行时缺二进制 | P0 验收含 pi-link 符合性测试 + 插件 bundling 真机路径 |
| npm 包名被抢注 | P1 前 `npm publish` 0.0.1 占位 |
| 三处版本不一致 | 全收敛进 release.sh，脚本内 grep 校验一致才继续 |
