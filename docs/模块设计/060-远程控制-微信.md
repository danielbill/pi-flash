## 0. 目标与边界

**目标**：在 pi-flash 内实现与 ZCode 微信 Bot 等价的体验——用一段微信文字聊天控制本机 pi-flash 会话：看状态、发消息、切模型/模式、停任务、审批扩展 UI 请求。

**范围（本次只做微信）**：

- ✅ 微信（iLink）渠道 + 文本交互 + 配置/扫码 UI
- ❌ 飞书 / Lark / Telegram / Webhook 四个渠道（ZCode 侧合计 3,696 行，全部不搬）
- ❌ 手机 Web 远控、zcode relay、`/remote/v4`（另一套协议，见 ZCode `AGENTS.md`「进程、协议与远程控制」）
- ❌ `streaming_card` 实时刷新卡片（**只有飞书有**，依赖 Feishu Card JSON 2.0，`shared/bots.ts:537-548` 显式把微信排除在外）

**非目标**：不追求富界面。微信侧本来就是**纯文本**（见 §1.2），"精致感"来自排版与信息架构，不是卡片。

## 1. 调研结论（2026-10-07，读源码）

### 1.1 没有第三方"优化"服务器

`packages/services/src/bots/` 全目录扫出的出站白名单只有 4 个官方开放平台：

| 域名 | 归属 |
|---|---|
| `https://ilinkai.weixin.qq.com` | **微信官方** iLink |
| `https://open.feishu.cn` / `accounts.feishu.cn` | 飞书 |
| `https://open.larksuite.com` / `accounts.larksuite.com` | Lark |
| `https://api.telegram.org` | Telegram |

没有 `zcode.z.ai`、没有 `z.ai`、没有 `bigmodel.cn`；**没有截图/Markdown 渲染服务**（全仓 bot 路径无 `resvg`/`sharp`/`puppeteer`/`markdown-it`）；**bots 目录 0 处遥测**。

三条反向证据：

1. **历史上依赖过第三方网关，后来主动摘掉**（`weixinProvider.ts:611`）：
   > `之前把 openclaw-weixin 当成本地 gateway 依赖，会导致 ZCode 不能独立完成微信接入。`
2. **多开去重用本地文件锁**（`channelRuntime.ts:110` → `<configdir>/bots-runtime-locks/<ns>/<hash>.lock` + `owner.json` + mtime 租约 10s 心跳 / 30s 租期），不是服务端协调。
3. **长轮询游标落在本地**（`botsService.ts:846-856` → `bots[botId].weixinGetUpdatesBuf`），不依赖任何服务端会话。

### 1.2 微信侧是纯文本

发送只有一条路（`weixinProvider.ts:611-628`）：

```ts
POST /ilink/bot/sendmessage
msg: { message_type: 2, message_state: 2,
       item_list: [{ type: 1, text_item: { text } }] }   // type 1 = 纯文本
```

唯一加工是 LF → CRLF 归一（`weixinProvider.ts:482-486`，否则 `/状态` 的行被折叠）。

**认知校准**：`getSupportedBotReplyGranularities`（`shared/bots.ts:537`）只给飞书 `streaming_card`，微信/Telegram 只有 `assistant_changes`（默认）/ `assistant_toolcalls_changes` / `summary_changes`。**微信上没有"实时刷新"，只有"分次发送"**——终态时 force flush。

### 1.3 "对齐 PC"的机制：同一份摘要原语，两个渲染器

| 原语 | 位置 | PC 端消费 | 微信端消费 |
|---|---|---|---|
| `getCompactToolCallSummary` | `shared/tool-call-summary.ts:207` | `ui/lib/toolCallSummary.ts`、`PermissionDialog.tsx` | `bots/replyFormatter.ts:246` |
| `getPermissionRequestPreview` | `shared/permission-request-preview.ts:338` | `ui/PermissionDialog.tsx:266,286,461` | `bots/replyFormatter.ts:191,216,316` |

输出样例（`replyFormatter.ts:246-252`）：

```text
- 完成 · Bash `npm test` · 🟢`+12` 🔴`-3`
变更摘要：3 个文件，🟢+12 🔴-3
- `src/app.ts` (🟢`+8` 🔴`-2`)
需要权限：写入中 src/app.ts
回复数字选择，0 取消。
```

**移植含金量在 B 层那 1,574 行纯字符串函数**——它们直接决定"对齐 PC 的精致感"，且无 IO、无状态，逐行翻译即可。

### 1.4 风险：iLink 是**私有接口**（唯一真风险）

防御式字段嗅探，不是有 SLA 的公开 API：

- `readNextBuf` 尝试 6 个候选：`get_updates_buf` / `buf` / `next_buf` / `nextBuf` / `getUpdatesBuf` / `syncKey`
- `readWeixinMessages` 尝试 5 个：`msgs` / `messages` / `updates` / `items` / `list`
- `message_id` 两级 × 3 个候选；`X-WECHAT-UIN`（随机 u32 base64）、`channel_version: "2.0.0"`、`AuthorizationType: ilink_bot_token`

协议一变就断，且无版本协商。**代码难度不是风险，协议稳定性才是**——所以 P0 必须先证伪（见 §5）。

接入门槛低：`GET /ilink/bot/get_bot_qrcode?bot_type=3` → `GET /get_qrcode_status?qrcode=` → `bot_token`，**无需向 ZCode/智谱注册任何东西**。

## 3. 目标架构

**放 `crates/app`，不开新 crate**。理由：审批桥要订阅 `SessionEvent::ExtUi`，那是 app 内部事件；且要复用 `i18n::t` / `theme` / `settings`。`services/` 按 ARCHITECTURE §2 定位是"无 UI 的纯函数"，本模块有实体与后台泵，归 `src/remote_control/`。

```text
crates/app/src/remote_control/
├── mod.rs             remoteControl 模块根：配置/启停/绑定码生成/状态栏入口 (=060)
├── wx/
│   ├── mod.rs         wxRemoteControl 子模块根
│   ├── provider.rs    iLink HTTP：getupdates/sendmessage/sendtyping/getconfig
│   │                  ← providers/weixinProvider.ts 674
│   ├── register.rs    扫码：get_bot_qrcode?bot_type=3 / get_qrcode_status
│   │                  ← providers/weixinRegistration.ts 184
│   ├── poller.rs      长轮询循环 + 游标后写 + 本地租约锁
│   │                  ← weixinChannelRuntime 343 + channelRuntime 290
│   └── wire.rs        有界请求封装（15s/90s 超时、abort 随生命周期）
│                      ← providers/providerRequest.ts 80
├── format/
│   ├── reply.rs       工具摘要/变更摘要/权限标题/3500 字分块   ← replyFormatter 421
│   ├── messages.rs    文案 + `{key}` 模板 → i18n::t           ← messages 267
│   ├── status.rs      /状态 六行卡 + 运行时长                  ← statusFormatting 181
│   └── summary.rs     摘要原语（若 app 尚无等价物则搬）        ← tool-call-summary 222
├── command.rs         命令解析（中英别名）+ 排队序             ← commandParser 101 + order 16
├── pipeline.rs        流式聚合 + 命令分发 + 选择菜单状态机     ← botsService 子集
├── bridge.rs          与 SessionRuntime 的桥（订阅事件/发命令/审批回填）
└── config.rs          config.json（token）+ state.json（BotState）落盘
```

**新增依赖**（`crates/app/Cargo.toml`，当前无 HTTP 客户端）：

| 用途 | 推荐 | 备选 | 说明 |
|---|---|---|---|
| HTTP 长轮询 | **`ureq`（阻塞）+ 专用 OS 线程** | `reqwest` + rustls | 90s 阻塞轮询天然适合同步 HTTP，**不把 tokio 拉进 GPUI 进程**；入站消息经 `futures::channel::mpsc` 推回 app |
| AES-128-ECB 解密（附件，P3 才要） | `aes` + `ecb` + `cbc`/pkcs7 | — | 只有附件下载需要，先不做 |

**状态落盘**：复用 `pi_link::paths`（`dir()` 已处理 `PI_FLASH_DIR` 隔离），新增两个入口：
`wxbot_config.json`（bot 配置 + token，**明文落本地**）/ `wxbot_state.json`（每聊天的 `BotState`）。不并入 `app-settings.json`，避免污染既有 schema。

**存活约束**（与 ZCode 相同）：ZCode 的 botsService 跑在 Electron host utility process，**app 关了 bot 就停**。pf 同理——轮询线程随 `pi-flash` 进程存活，不做常驻服务。要在 UI 上明示这个约束。

### 4.1 审批桥（本模块最关键的复用点）

pi **没有内置逐次工具审批**（`vendor/pi/.../security.md:3`：`does not ask for approval before every tool call`）。但 `extensions.md:166` 给了标准形态：**permission 扩展在 `tool_call` handler 里 `ctx.ui.confirm(...)`**，未确认就 `return { block: true, reason }`。

而 `ctx.ui.confirm()` 落到 wire 就是 `extension_ui_request { method: "confirm" }` → `Event::ExtensionUi`。**这条链路 pi-flash 已经全部打通**：

```text
permission 扩展(tool_call) ── ctx.ui.confirm
      ↓  extension_ui_request
Event::ExtensionUi(req)                    session/runtime.rs:909
      ↓  cx.emit(SessionEvent::ExtUi)
actions_runtime.rs:48-59
      ├─ 会话 active  → chat.on_ext_ui(req)      (桌面弹窗)
      └─ 会话 parked  → runtime.ext_queue.push   (徽标排队，切进去才 surface)
      ↓
ext_ui_actions.rs:91 ext_dialog = Some(req)
ext_ui_actions.rs:110 Command::ExtensionUiResponse { id, value, confirmed, cancelled }
```

**微信接入点就在 `SessionEvent::ExtUi` 这一个事件上**：该会话已绑定微信 context 时，除了桌面弹窗，同时由 `bridge.rs` 把 `req` 格式化成微信文本菜单（`Select` → 编号菜单 + 0 取消；`Confirm` → 回复 1/2；`Input` → 直接回文本），用户回数 → 走**同一条** `ext_respond` 出口回填。**协议零改动**，桌面端与微信端天然同一队列（`ext_queue` 语义与 ZCode 的 `pendingPermissionOptions` 同构）。

**依赖前置**：需要一个小的 permission 扩展（形态照 `full_activate.ts`，编译进二进制 / release 落 `~/.pi-flash/`，绝对路径经 `-e` 传入），否则 pi 根本不会发 confirm 请求。**这是档 2 的硬前置，不是可选项。**

### 4.2 状态模型（照搬 `shared/bots.ts:177-191`）

```rust
// remote_control/config.rs —— 每个微信聊天一个 context
pub struct BotState {
    pub bot_id: String,
```

## 6. 四条易踩坑（ZCode 注释直译，必须照做）

1. **Flush 边界不按 chunk**（`replyFormatter.ts:258-265`）
   > `provider chunk 常按词或子词到达，非终态时必须继续留在 assistantReplyBuffer 里合并；真正的发送边界由 tool_call / task_complete 等 force flush 决定。`
2. **游标处理完再写**（`weixinChannelRuntime.ts:155-163`）—— 先写 `get_updates_buf` 再回复，进程中途失败会跳过未完成消息。
3. **一切 provider 交互必须有界**（`providerRequest.ts:44-47`）
   > `第三方 Bot API 不一定会自行结束悬挂请求。所有回调 ACK 和出站消息都必须有界，否则单个请求会占住 actor 串行队列，后续权限、问答和计划审批都无法继续。`
4. **锁 I/O 失败必须退避重试，不能让后台循环退出**（`weixinChannelRuntime.ts:70-77`）—— 每个窗口都有独立 host，一次锁失败退出 = bot 静默死掉。
