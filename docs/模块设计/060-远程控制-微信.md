## 0. 目标与边界

**目标**：在 pi-flash 内实现与 ZCode 微信 Bot 等价的体验——用一段微信文字聊天控制本机 pi-flash 会话：看状态、发消息、切模型/模式、停任务、应答扩展 UI 请求。**工具调用不审批**（pi 原则，见 §4.1 翻案）。

**范围（本次只做微信）**：

- ✅ 微信（iLink）渠道 + 文本交互 + 配置/扫码 UI
- ❌ 飞书 / Lark / Telegram / Webhook 四个渠道（ZCode 侧合计 3,696 行，全部不搬）
- ❌ 手机 Web 远控、zcode relay、`/remote/v4`（另一套协议，见 ZCode `AGENTS.md`「进程、协议与远程控制」）
- ❌ `streaming_card` 实时刷新卡片（**只有飞书有**，依赖 Feishu Card JSON 2.0，`shared/bots.ts:537-548` 显式把微信排除在外）

**非目标**：不追求富界面。微信侧本来就是**纯文本**（见 §1.2），"精致感"来自排版与信息架构，不是卡片。

## 1. 调研结论（2026-10-07，读源码）

### 1.1 没有第三方"优化"服务器

`packages/services/src/bots/` 全目录扫出的出站白名单只有 4 个官方开放平台：

| 域名 | 归属 |
|---|---|
| `https://ilinkai.weixin.qq.com` | **微信官方** iLink |
| `https://open.feishu.cn` / `accounts.feishu.cn` | 飞书 |
| `https://open.larksuite.com` / `accounts.larksuite.com` | Lark |
| `https://api.telegram.org` | Telegram |

没有 `zcode.z.ai`、没有 `z.ai`、没有 `bigmodel.cn`；**没有截图/Markdown 渲染服务**（全仓 bot 路径无 `resvg`/`sharp`/`puppeteer`/`markdown-it`）；**bots 目录 0 处遥测**。

三条反向证据：

1. **历史上依赖过第三方网关，后来主动摘掉**（`weixinProvider.ts:611`）：
   > `之前把 openclaw-weixin 当成本地 gateway 依赖，会导致 ZCode 不能独立完成微信接入。`
2. **多开去重用本地文件锁**（`channelRuntime.ts:110` → `<configdir>/bots-runtime-locks/<ns>/<hash>.lock` + `owner.json` + mtime 租约 10s 心跳 / 30s 租期），不是服务端协调。
3. **长轮询游标落在本地**（`botsService.ts:846-856` → `bots[botId].weixinGetUpdatesBuf`），不依赖任何服务端会话。

### 1.2 微信侧是纯文本

发送只有一条路（`weixinProvider.ts:611-628`）：

```ts
POST /ilink/bot/sendmessage
msg: { message_type: 2, message_state: 2,
       item_list: [{ type: 1, text_item: { text } }] }   // type 1 = 纯文本
```

唯一加工是 LF → CRLF 归一（`weixinProvider.ts:482-486`，否则 `/状态` 的行被折叠）。

**认知校准**：`getSupportedBotReplyGranularities`（`shared/bots.ts:537`）只给飞书 `streaming_card`，微信/Telegram 只有 `assistant_changes`（默认）/ `assistant_toolcalls_changes` / `summary_changes`。**微信上没有"实时刷新"，只有"分次发送"**——终态时 force flush。

### 1.3 "对齐 PC"的机制：同一份摘要原语，两个渲染器

| 原语 | 位置 | PC 端消费 | 微信端消费 |
|---|---|---|---|
| `getCompactToolCallSummary` | `shared/tool-call-summary.ts:207` | `ui/lib/toolCallSummary.ts`、`PermissionDialog.tsx` | `bots/replyFormatter.ts:246` |
| `getPermissionRequestPreview` | `shared/permission-request-preview.ts:338` | `ui/PermissionDialog.tsx:266,286,461` | `bots/replyFormatter.ts:191,216,316` |

输出样例（`replyFormatter.ts:246-252`）：

```text
- 完成 · Bash `npm test` · 🟢`+12` 🔴`-3`
变更摘要：3 个文件，🟢+12 🔴-3
- `src/app.ts` (🟢`+8` 🔴`-2`)
需要权限：写入中 src/app.ts
回复数字选择，0 取消。
```

**移植含金量在 B 层那 1,574 行纯字符串函数**——它们直接决定"对齐 PC 的精致感"，且无 IO、无状态，逐行翻译即可。

### 1.4 风险：iLink 是**私有接口**（唯一真风险）

防御式字段嗅探，不是有 SLA 的公开 API：

- `readNextBuf` 尝试 6 个候选：`get_updates_buf` / `buf` / `next_buf` / `nextBuf` / `getUpdatesBuf` / `syncKey`
- `readWeixinMessages` 尝试 5 个：`msgs` / `messages` / `updates` / `items` / `list`
- `message_id` 两级 × 3 个候选；`X-WECHAT-UIN`（随机 u32 base64）、`channel_version: "2.0.0"`、`AuthorizationType: ilink_bot_token`

协议一变就断，且无版本协商。**代码难度不是风险，协议稳定性才是**——所以 P0 必须先证伪（见 §5）。

接入门槛低：`GET /ilink/bot/get_bot_qrcode?bot_type=3` → `GET /get_qrcode_status?qrcode=` → `bot_token`，**无需向 ZCode/智谱注册任何东西**。

## 3. 目标架构

**放 `crates/app`，不开新 crate**。理由：扩展 UI 呈现要订阅 `SessionEvent::ExtUi`，那是 app 内部事件；且要复用 `i18n::t` / `theme` / `settings`。`services/` 按 ARCHITECTURE §2 定位是"无 UI 的纯函数"，本模块有实体与后台泵，归 `src/remote_control/`。

```text
crates/app/src/remote_control/
├── mod.rs             remoteControl 模块根：配置/启停/绑定码生成/状态栏入口 (=060)
├── panel.rs           左列「微信」面板（DockPanel::Wx；2026-10-23 自设置页迁入）
├── wx/
│   ├── mod.rs         wxRemoteControl 子模块根
│   ├── provider.rs    iLink HTTP：getupdates/sendmessage/sendtyping/getconfig
│   │                  ← providers/weixinProvider.ts 674
│   ├── register.rs    扫码：get_bot_qrcode?bot_type=3 / get_qrcode_status
│   │                  ← providers/weixinRegistration.ts 184
│   ├── poller.rs      长轮询循环 + 游标后写 + 本地租约锁
│   │                  ← weixinChannelRuntime 343 + channelRuntime 290
│   └── wire.rs        有界请求封装（15s/90s 超时、abort 随生命周期）
│                      ← providers/providerRequest.ts 80
├── format/
│   ├── reply.rs       工具摘要/变更摘要/权限标题/3500 字分块   ← replyFormatter 421
│   ├── messages.rs    文案 + `{key}` 模板 → i18n::t           ← messages 267

│   └── summary.rs     摘要原语（若 app 尚无等价物则搬）        ← tool-call-summary 222
├── command.rs         命令解析（中英别名）+ 排队序             ← commandParser 101 + order 16
├── pipeline.rs        流式聚合 + 命令分发 + 选择菜单状态机     ← botsService 子集
```

**新增依赖**（`crates/app/Cargo.toml`，当前无 HTTP 客户端）：

| 用途 | 推荐 | 备选 | 说明 |
|---|---|---|---|
| HTTP 长轮询 | **`ureq`（阻塞）+ 专用 OS 线程** | `reqwest` + rustls | 90s 阻塞轮询天然适合同步 HTTP，**不把 tokio 拉进 GPUI 进程**；入站消息经 `futures::channel::mpsc` 推回 app |
| AES-128-ECB 解密（附件，P3 才要） | `aes` + `ecb` + `cbc`/pkcs7 | — | 只有附件下载需要，先不做 |

**状态落盘**：复用 `pi_link::paths`（`dir()` 已处理 `PI_FLASH_DIR` 隔离），新增两个入口：
`wxbot_config.json`（bot 配置 + token，**明文落本地**）/ `wxbot_state.json`（每聊天的 `BotState`）。不并入 `app-settings.json`，避免污染既有 schema。

### 4.1 扩展 UI 呈现（~~审批桥~~，2026-10 翻案）

pi **没有内置逐次工具审批**（`vendor/pi/.../security.md:3`：`does not ask for approval before every tool call`），且**内置于 pi 的原则就是如此**：安全边界由「挂载哪些工具/扩展」决定（`--tools` / `-e` / 预设），而不是逐次确认。初版曾照 ZCode 的 permission 模型加了逐次审批扩展（`wx_permission.ts`），对**每个**工具调用弹 `ctx.ui.confirm` —— 实测连 pi 内置只读工具（read/ls/grep/find 均无 annotations）都要弹，桌面与微信两头被打断，且这不是 pi 的行为。**2026-10-08 翻案：该扩展已删除，任何档位都不挂 permission 门禁，两端（桌面/微信）都遵循 pi 原则。**

保留下来的是 pi 原生的 **extension UI 呈现链路**：用户真实安装的扩展调用 `ctx.ui.confirm/select/input` 时（pi 自己的机制），请求照常呈现——

```text
用户扩展(ctx.ui.*) ── extension_ui_request
      ↓
Event::ExtensionUi(req)                    session/runtime.rs:909
      ↓  cx.emit(SessionEvent::ExtUi)
actions_runtime.rs:48-59
      ├─ 会话 active  → chat.on_ext_ui(req)      (桌面弹窗)
      └─ 会话 parked  → runtime.ext_queue.push   (徽标排队，切进去才 surface)
      ↓
ext_ui_actions.rs:91 ext_dialog = Some(req)
ext_ui_actions.rs:110 Command::ExtensionUiResponse { id, value, confirmed, cancelled }
```

**微信接入点仍在 `SessionEvent::ExtUi` 这一个事件上**：该会话已绑定微信 context 时，除了桌面弹窗，同时由 `bridge.rs` 把 `req` 格式化成微信文本菜单（`Select` → 编号菜单 + 0 取消；`Confirm` → 回复 1/2；`Input` → 直接回文本），用户回数 → 走**同一条** `ext_respond` 出口回填。**协议零改动**，桌面端与微信端天然同一队列（`ext_queue` 语义与 ZCode 的 `pendingPermissionOptions` 同构）。这是「把 pi 已有的对话框如实搬到另一端」，不是发明审批策略。

#### 接口实测

| 接口 | 方法 / 头 | 真实响应字段 |
|---|---|---|
| `/get_bot_qrcode?bot_type=3` | GET + `iLink-App-ClientVersion: 1` | `qrcode`(32 位 hex) · `qrcode_img_content`(**URL**) · `ret:0`；**无 `expires_in`** → ZCode 的 `?? 120s` 兜底生效 |
| `/get_qrcode_status?qrcode=` | GET 同上 | `status` → `bot_token`(58 字符) · `ilink_bot_id` |
| `/getupdates` | POST + `ilink_bot_token` / `Bearer` / `X-WECHAT-UIN` | 顶层 **`msgs` + `sync_buf` + `get_updates_buf`**；请求 `{base_info, get_updates_buf}` |
| `/sendmessage` | POST 同上 | 响应 `{message_id}`；请求 `{base_info, msg{…}}` |

`qrcode_img_content` = `https://liteapp.weixin.qq.com/q/7GiQu1?qrcode=<id>&bot_type=3`，该 URL 返回
`text/html` 落地页 → **必须把它编码成二维码**（与 ZCode `QRCode.toDataURL(result.qrUrl)` 同做法，

## 6. 四条易踩坑（ZCode 注释直译，必须照做）

1. **Flush 边界不按 chunk**（`replyFormatter.ts:258-265`）
   > `provider chunk 常按词或子词到达，非终态时必须继续留在 assistantReplyBuffer 里合并；真正的发送边界由 tool_call / task_complete 等 force flush 决定。`
2. **游标处理完再写**（`weixinChannelRuntime.ts:155-163`）—— 先写 `get_updates_buf` 再回复，进程中途失败会跳过未完成消息。
3. **一切 provider 交互必须有界**（`providerRequest.ts:44-47`）
   > `第三方 Bot API 不一定会自行结束悬挂请求。所有回调 ACK 和出站消息都必须有界，否则单个请求会占住 actor 串行队列，后续权限、问答和计划审批都无法继续。`
4. **锁 I/O 失败必须退避重试，不能让后台循环退出**（`weixinChannelRuntime.ts:70-77`）—— 每个窗口都有独立 host，一次锁失败退出 = bot 静默死掉。

## 9. 真机联调与两处断链修复（2026-10-23）

**正名背景**：本文档 premise 时期的调研误判已纠正（见文首横幅）——ZCode 的「远程控制」是 H5 工作台 + 自建 relay，与本模块无关；本模块 = 微信 Bot 渠道。

### 修复①：显式启用被 SELF_START 一刀切误杀

`ensure_transport` 的 `SELF_START=false` 早退把三条启动路径全堵死：设置页开关、扫码成功、自动化 `wx.enable` 都拉不起渠道——扫码"成功"关窗后轮询永不启动，表现即「绑定成功但消息石沉大海」。拆为两条路径：`ensure_transport`（开机自启，受门控）与 `start_transport_from_state`（显式启用，不受门控）；三处显式入口统一置 `wants_start` 由 200ms 泵执行——测试可断言意图而不真起线程。

### 修复②：私聊出站全丢（「发了没反应」真凶）

`send_loop` 硬性要求 state 里有 `chat_id` 才发送，但**私聊（决策 5：唯一支持形态）`chat_id` 恒为 `None`**——所有回执被静默丢弃，`warn_once` 打在 GUI 进程看不见的 stderr 上。CLI `wxprobe send` 用 `user_id` 能发通、app 发不出，不对称即证据。修复：对端解析 `chat_id`（群聊 room id）→ `user_id`（私聊对端，入站 from_user_id 随 ack 回写）两级回退。

### 新增：微信默认会话（bot 语境）

「PF 启动时应该有一个默认的微信对话，否则微信跟谁说话」——入站投递原是「始终投当前活跃会话」（1b 简化），桌面一切会话微信线就漂移。现对齐 ZCode「bot 自己的 activeTask」：

- `RemoteControl.wx_session` + state 持久化（`session_key`）；渠道启用后**泵第一拍认领**当前活跃会话，重启跟同一条线
- `target_key`：`wx_session` → `bound` → `active_key` 兜底；`agent_running_now` / `status_reply` / pump 运行态回填全部改读目标会话
- `/新建` = `new_draft_detached` 给微信线开新草稿，**不抢桌面焦点**；`/task` 选已开会话只改指向，未开会话才走打开；目标被删自愈回退
- 草稿键 `draft-N` → 文件路径键的迁移在 `on_file_bound` 同步跟随，归属不悬空

### 新增：自动化 `wx.enable`

入口全隐藏后（2026-10-10 定），重启实例没有任何 UI 路径能起渠道。新增 `wx.enable`（返回 `running` 字段；启动由泵下一拍完成）与 `scripts/pif_auto.mjs`（TCP 行 JSON 客户端：实例发现覆盖 debug 的 `pi-flash-dev/automation/`，响应记录无 `type` 字段按 `ok` 识别）。

### 真机状态（2026-10-23 晨）

扫码绑定（新 bot `92b296a…`）→ 渠道起、轮询锁在位、游标推进、入站消息（"收到"）确认到达并可解析——**入站半程全通**；出站半程待 `send_loop` 修复后的新实例复验（微信发消息 → 激活回执 → /状态 → 任务回推）。

### 修复③：换绑后旧会话状态残留 + 渠道不重启（2026-10-23 午，「运行中却没反应」真凶）

真机现象：面板「渠道：运行中」+ 扫码绑定成功，微信发消息毫无反应。dump 逆推完整链条：

1. 渠道在扫码**前**被开关拉起，`poll_loop` 拿的是 state 里**旧 bot** 的 token；用户重扫码注册出新 bot（每次扫码会让同账号旧 bot 会话在服务端失效）后，getupdates 从第 3 拍起全部 `errcode:-14 session timeout`（wxprobe-dump 001/002 正常、003 起全 51 字节 -14）。
2. 扫码成功后 pump 的 `wants_start && !is_running()` 见渠道还活着就跳过——**新 token 永远装不进去**，旧 token 死循环重试。
3. `register.rs` 成功分支只覆写 `bot_token/bot_id/bot_user_id`，**不清 `buf`/`chat_id`/`user_id`/`context_token`**——就算重启，新 token 配旧 bot 游标照样被拒（state `buf` base64 里嵌着旧 bot `2b296a82465@im.bot`，与现 bot 不同）。
4. 三重不可见：`poll_loop` 的 `Err` 分支 `let _ = e;` 不打 stderr；面板「运行中」只看 `transport.is_some()`；传输层失败的请求连 dump 都不落（dump 只记完成交换）。

修复（三层）：`register.rs` 扫码成功即清 `reset_session_fields`（buf/chat_id/user_id/context_token，`session_key` 是 PF 侧归属保留）；app 泵在 QR Done 时 `force_restart_if_token_changed`（运行中渠道 token ≠ state 现值 → drop 重拉）；`Transport.last_poll_error` 每拍同步到面板「最近错误：…」+ `warn_once` 打 stderr。

### 复验与新发现（2026-10-23 午）

- ~~出站半程已验证~~ **修正**：`sendmessage` 拿到 `message_id` ≠ 手机收到——见修复⑤，`message_id` 只是受理回执。

### 修复⑤：出站「受理不投递」真凶——client_id 固定复用（2026-10-23 午后）

修复④后真机复测：消息进 pi、模型回复、`sendmessage` 返回 `message_id`——**但手机永远收不到**（CLI 直发探针同样石沉大海）。请求结构与 10-07 P0「手机能看到」的探针、11:14/12:13 两次成功投递逐字段一致，唯一协议偏离：**`client_id` 是 state 里写死的稳定实例 id，而 iLink 协议参考（epiral/weixin-bot PROTOCOL.md）明确 `client_id` = "unique_id"，每条消息必须唯一**。固定值长期复用后，iLink 受理（返回新 message_id）但不投递。对照实验钉死：同一 context_token、同一分钟内——固定 client_id 的消息不达，唯一 client_id 的两条（含 `from_user_id` 照填 bot id 的）全部送达。

修：`poller::send_text` 内部把传入 client_id 拼成 `{client_id}-{millis}-{seq}`（毫秒 + 进程内序列号），app 的 send 线程与 CLI 同走此路径，调用方零改动。附带旁证：`getconfig` 用同 ctx 返回 `ret:0` + typing_ticket——受理不投递期间会话与 context_token 都是活的，排除了 token/会话过期。

### 修复④：微信线后台会话化（2026-10-23 午后，「回复石沉大海」三缺陷）

修复③后真机复测：微信发「刚刚」→ 只收到一句 pi 启动横幅碎片「🔌 MCP: 1 server enabled」（带 ANSI 色码，全文在 pi 代码/全部会话文件/扩展里都不存在，系运行时拼接的启动输出）；再发「？？？？啥意思！」→ 石沉大海。会话文件还原真相：**第二条消息完整进入会话并得到完整回复**（thinking → bash 工具 → 最终答复落在会话文件里），但回复从未发回微信；第一条则根本没进 pi。三个独立缺陷：

1. **出站回推只认桌面选中态**（主犯）：`pool.rs` 的 Assistant 转发门是 `is_active`，入站却固定投 `wx_session`——多项目常态下桌面一切换，微信线的回复全部静默丢失。修：口径对齐入站（`is_active || wx_session` 放行）；缓冲加 `buf_key` 双源防串线（换来源先冲旧来源）；泵的轮末冲刷改看**缓冲来源**的运行态（否则桌面流式文本被 200ms 一拍冲成碎片）。
2. **投递静默丢失**：目标会话只是**没打开**（runtime 不存在，重启后常态）时 `send_wx` 自愈兜底落空即丢，`send_remote_text` 失败也只打 stderr。修：会话文件还在 → `open_session_detached` **后台唤醒**（建 runtime + 尾窗快照，不动 `active_key`/`ws.cwd`/焦点）再投递；文件真被删才走既有改绑自愈；失败必有微信端回执（`RemoteSend` 三态区分排队/失败，排队不发回执防刷屏）。
3. **轮外文本泄漏**：启动横幅从 assistant 文本通道混进回复缓冲。修：出站门只在**发送轮内**（`agent_running`）转发，空闲期文本不进缓冲。

**正名**：微信线自此是真正的**后台会话**——bot 语境独立于桌面选中态（对齐 ZCode「bot 的 activeTask」），桌面切到哪都不影响微信收发。
