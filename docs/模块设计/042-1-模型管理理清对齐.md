## 2 不变量（两条铁律）

1. **用户自己定义的明文不看、不改、不删**——`models.json` 与 `auth.json` 里非 PF 标记的内容一律只读。
2. **PF 保存的 apikey 只进系统钥匙库**，盘上永不出现明文；pi 通过 `!command` 在请求时取回。

推论：PF 只写/只删**带自己标记**的条目（§3.1）。

## 3 凭据模型

### 3.1 标记与形态

PF 写入的条目：

```json
{ "deepseek": { "type": "api_key", "key": "!pf-secret get deepseek" } }
```

- 标记判据：`type == "api_key"` 且 `key` 以 `!pf-secret get ` 开头。
- 秘密只存在钥匙库（条目名沿用 `env_var_name(provider)`）。
- 依据：pi `AuthStorage.read()` 对 api_key 的 key 走 `resolveConfigValue`，`!` 前缀即“执行命令取 stdout 作为 key”；命令失败 = 该商未配置（不会把命令串当 key 发出）。
- helper：`pf-secret` 独立小二进制随安装分发，形如 `!<install-dir>/pf-secret.exe get <provider>`（Windows 走 Git Bash `bash -c`，路径用正斜杠 + 单引号）。
- 换 key 后**需重开会话生效**（pi 的 `commandResultCache` 是进程级），与既有 env 注入语义一致。

### 3.2 写 / 删 / 展示

| 动作 | 规则 |
|---|---|
| 保存 key | ① 钥匙库写入 + 读回校验 → ② 锁内写 `auth.json` 条目 → ③ 失败回滚钥匙库。目标条目**非 PF 标记**时先弹确认“该商已有你手写的凭据，覆盖？” |
| 移除 / 断开连接 | 只删 PF 标记条目（类型+标记双守卫）+ 删钥匙库条目。非标记条目：不删、不报错，提示由用户自行维护 |
| 详情页预填掩码 | 非标记明文条目 → 展示该值掩码；PF 标记条目 → 从钥匙库解出掩码。只读 |
| 失效校验 | 启动/打开设置页时校验：标记条目指向的 helper 存在、钥匙库条目在。对不上给明确文案，不静默 |


## 模型列表管理
分两种内置和自定义
1、内置Provider的模型列表来自Pi自带，用户选中任何一个Provider，不用apikey即可罗列出所有该内置Provider下的所有模型
2、自定义Provider的模型列表，根据用户手填的baseurl尝试从获得官方模型清单，有则自动列出，无则用户手工添加。

不论是内置的还是自定义的， 用户从模型列表中选中的模型才保存至models.json
在PF数据目录下增加一个 custom-provider.json， 用来存放自定义Provider的模型列表，自动拉取或用户添加的自定义模型都存放其中。删除自定义Provider时，整个条目删除。用户可以在自定义模型列表中选择想要激活的模型，on后存入models.json。



## 4 模型/provider 模型

- 自定义 provider/模型全部写 `models.json`：**整份草稿保存**，文件存在但读不出来 → 拒写（pi-web `ModelsConfigReadError` 同款守卫）。
- 模型清单来源收敛为：pi 进程答案（`get_available_models`）优先，冷启动回落到磁盘（`models-store.json` + `models.json`）。
- **修订（2026-11-01）**：本页曾随「唯一真相源」删除 catalog-cache 缓存层与 registry 静态目录保底，导致 27/40 内置商（无探查端点表条目）既无「获取模型」能力又无保底目录（正式包 Z.AI Coding CN「暂不支持自动获取模型目录」事故）。当日恢复 010-启动.md §4.1 缓存层（runtime 答复/手动拉取/启动 sweep 三路回写）+ 启动后台 sweep；「唯一真相源」语义不变——缓存只是 `models-store.json + models.json` 之外的 PF 自有新鲜度层，落 `~/.pi-flash/` 不碰 pi 文件。
- 白名单 `enabledModels` 语义保留（写 pi `settings.json`），对齐 pi-web `enabled-models`。
- 无 `removed_providers` 墓碑：移除 = 删凭据 + 从 `models.json` 删该商。

## 5 热路径约束

- 启动不做任何钥匙库/`auth.json` 写入；迁移器后台低优先级。
- 写 `auth.json` / `models.json` 只在用户动作时发生（保存/移除/新增 provider）。

## 6 测试钉子（pi-link 符合性）

1. 临时 HOME 写一条 `!cmd` 凭据 → pi 判“已配置”（`pi auth check --json` ready）；helper 缺失 → not ready。
2. `ReadOnlyAuthStorage` 不执行 `!command`（元数据读取不触发 shell）。
3. 锁协议：PF 写入与 pi 并发写不互相覆盖（OAuth 轮换场景）。
4. `models.json` 不可读时保存被拒（不覆盖）。

## 7 已知不满足项（明示，不当 bug）

- 跨机 / 容器 / 远程使用 pi-web 时，PF 管理的商显示“未配置”（钥匙库与 helper 不在场）。提供显式动作【导出明文 auth.json】兜底，默认不导出。
- helper 生命周期与安装耦合：auth.json 指向的 helper 不存在时该商失效；由 §3.2 失效校验兜底提示。


## 8 三处受保护改造（**不改**）

只允许换数据源（`mj_doc()` / `mj_write()` 数据源 = `models.json`），不改布局 / 交互 / 字段语义：

1. 自定义 Provider 详情页（`custom_models.rs::mj_provider_editor`）：头行 name+【移除】、API Key 段、Base URL、API 下拉、操作栏[测速][保存][+模型]、高级设置、可用模型区。
2. 模型详情页（`mj_model_modal_overlay`）：500×500 弹窗，ID / 上下文 / 最大输出 / 能力(text·image) / 推理，[自动填参][测试][保存][移除]。
3. 自动填参（`mj_catalog_fill` → `pi_link::openrouter::resolve_many`）：数据源 = OpenRouter（单模型直查 + 全量兜底），替代 models.dev；覆盖 `contextWindow` / `maxTokens` / `input(text,image)` / `reasoning` / `name`，`cost` 只填空。

`input` 只允许 `text` / `image`（pi `MODEL_INPUT_MODALITIES` 仅此两项；多写会让整份 `models.json` schema 校验失败）。

### 8.1 填参检索键：官方 id 常是家族名，版本名才拿得到具体型号（2026-11-01）

商家 `/models` 返回的 **id 是家族名**（DeepSeek 的 `deepseek-flash`，以后每个
flash 版本都叫它），版本信息只在 **name** 里（`DeepSeek-V4.1-Flash`）。OpenRouter
目录对家族名往往只有 `~deepseek/deepseek-flash-latest` 这类「最新版」别名
通配条目（参数是聚合值），对版本名才有具体型号条目（真值）：

| 目录条目 | ctx | maxTokens |
|---|---|---|
| `~deepseek/deepseek-flash-latest`（别名） | 1048576 | **943718** |
| `deepseek/deepseek-v4.1-flash`（具体） | 1048576 | **393216** |

铁律：**只换查询键，不换字段值**。

- 详情页「模型ID」框与落盘永远是**官方列表值**（id 原样），保存链路零改动；
- `model_ref::query_candidates(id, name)` 产出并列检索键 `[官方 id, slug(name)]`
  （`slugify`：剥厂商前缀、小写、空白/下划线转 `-`）；
- `openrouter::resolve_many` 逐键查询、**具体型号优先于别名通配**（同档看候选
  顺序；全部只拿到别名才用第一个别名命中）——id 本身命中具体型号时行为与旧版
  完全一致；
- 这是**纯后台机制**：UI 不显示、不提示、不让用户知道（用户定稿：无用的提示
  只会让人困惑）；name 缺（手输新模型）时退化成单键查询；
- 点列表进详情的账本匹配：先精确 id；兜底只认 **id**（忽略大小写 / slug 等价）
  且必须**唯一**，多条相似一律不猜 → 退回只读的 pi 定义视图。**name 绝不参与
  匹配**——账本 name 是显示字符串，曾因它把「点 GLM-4.6V」串成账本里
  `id=glm-5.3-flash-free, name=GLM-4.6V` 那条，弹出一个莫名其妙的 free 模型。

## 模型列表架构定稿（2026-11-01）

列表 = 展示层，models.json = 用户勾选。二者分离：

| | 模型列表（罗列）来源 | models.json 写入 |
|---|---|---|
| 内置 Provider | pi 自带注册表（`registry-cache.json` 的静态 `models[]`，**无需 apikey**）∪ 进程答案/models-store 目录 | **零写入**——pi 静态注册表即持久态；勾选只写 `enabledModels` patterns（pi available 门） |
| 自定义 Provider | 骨架常驻 models.json；模型**完整定义**（自动拉取 / 手填 / 手调参数）全部存 PF 侧 **`~/.pi-flash/custom-provider.json`**（清单仓，删商时整条目删）；列表 = 仓内全部条目 | 勾选 on → 把仓里的定义**原样复制**进 `models[]`（缺 api/baseUrl 由骨架补齐）；off → 只删 models.json 投影，**定义留仓**（off/on 往返不丢参数）；`models[]` 空则骨架保留 |

- 罗列���点：`settings/models.rs::provider_models_for_list`（账本 ∪ 目录 ∪ registry 静态 ∪ 清单仓，按 id 去重）；静态/仓**不进** `catalog_for`/`Globals.models`（picker 非虚拟化，性能铁律）。已配置凭据的内置商经 `catalog_with_ledger` 并入静态，否则其模型不在 `mc_refs` 里、勾选链静默丢弃。
- 清单仓写入点：探测 Ok（只补缺不覆盖手调）/ 模型详情保存（恒写仓；已勾选的同步 models.json）/ 手填 +模型（显式创建 = 勾选，仓 + models.json 双写）/ 模型详情【移除】（仓 + models.json 同删）。**不是 051 账本复活**：pi 仍只读 models.json，仓不参与注册、不注入、不碰凭据。
- 侧栏成员资格：内置商 = 有凭据；自定义商 = models.json 有条目（`is_custom`）；内置商在 models.json 的覆盖条目不构成成员。
- 勾选双写：`mc_toggle_model` = enabledModels patterns（现状）+ 自定义商 `mj_materialize_selection`（内置商不物化）。
- 内置商「获取模型/刷新」钮：**隐藏不删**（`Chat::BUILTIN_FETCH_UI = false`），`mc_probe_start` 收缩为保存 key 后的连通检查，不落目录。
- 13 条手写端点白名单已废；端点单源 = registry dump 的 SDK baseUrl/api（`registry::models_list_target`）。
- 事故记录：042-1 曾把拉取目录整批写入 models.json（OpenRouter 400+ 条会被整份复制进 pi 配置），本定稿根治。
