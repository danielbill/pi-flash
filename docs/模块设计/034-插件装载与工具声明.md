# 插件装载与工具声明模型（034）

> 起因：确认「默认把插件全装上」是 pi 的机制，然后做更精细化的设计。
> 实测环境：vendored pi 1.0.0 + 真实 agent dir（8 个 npm 包 + 个人扩展/skills）；
> 探针脚本 `D:\ai_workspace\pi_work\tmp_probe\fp`（`probe.ts` 落
> `getAllTools()/getActiveTools()/getCommands()`）。日期 2026-10-07。

## 1. 现状确认（是的，默认全装）

代码路径：

```
agent_session::spawn_with  →  client::spawn(cwd, args, load_extensions_enabled())
services::workspace::load_extensions_enabled()  =  app_settings.load_extensions
                                                 .unwrap_or(true)   // None = 开
```

`load_extensions = true`（默认）→ **不加 `-ne`** → 完全按 pi 自己的默认装载：

- `<agent dir>/extensions/`（发现）+ `settings.json` 的 `packages`（配置，全局 + 项目）+ 4 个内置扩展；
- `skills` / `prompts` / `themes` 的发现与配置（`<agent dir>/skills`、`.agents/skills`、项目 `.pi/…`、包内资源）；
- `AGENTS.md` / `CLAUDE.md` 上下文文件。

**工具预设管不到这里**：`configured/chat-only/read-only/default/full` 只是往 spawn 里加
`--tools` / `--no-tools`（`configured` 什么都不加 = 交给 `settings.defaultTools`），
与扩展装载无关。但要注意 `--tools` 是**注册级硬 allowlist**（031 A–H 组实测）：
`default/full/read-only/chat-only` 这些档会把插件工具**连同注册一起挡掉**，
只有 `configured`（不发 `--tools`）和新的 `full+plugins`（不发 `--tools` + `setActiveTools`）
能同时拥有插件工具。

实测对照（同一台机器、同一 agent dir）：

| 模式 | 注册工具 | **进模型（active）** | 命令数 | 个人 skills |
|---|---|---|---|---|
| P1 默认 = `configured` 档 | 96 | **39** | 35 | 全在 |
| P2 `-ne`（隔离） | 9 | 5 | 1（探针） | **仍在（14 条 `skill:*`）** |
| P3 `-ne` + 1 个包 | 16 | 11 | 3 | 仍在 |

两点值得记住：

1. **`-ne` 只关扩展**（发现 + 配置 + 内置）；skills / prompt 模板 / 主题各有自己的开关：
   `-ns` / `-np` / `--no-themes`。所以在 `full+plugins` 档里个人 skills 照常可用，
   不会因为 `-ne` 消失。
2. 默认档的代价是 **39 个工具说明进模型**（computer_use 30 个 + agent_browser 8 个 +
   编辑工具 8 个 + web 4 个 + plan/mcp/codemode…）。这才是「插件全装」的实际成本。

设置·插件页的启停是**全局**语义：往 settings.json 里把该包写成
`{source, extensions:[], skills:[], prompts:[], themes:[]}`（pi 认这个「资源置空」
过滤；E 组对照验证 disabled 包不加载）。它改不了单个会话。

### 1.1 `full` 档实测：插件全装，只有工具被掐

原样复现 app 的 `full` spawn（真实 agent dir，`--tools bash,read,edit,write,grep,find,ls`）：

| | `configured` | `full` |
|---|---|---|
| 注册工具 | 96 | **7**（bash,read,edit,write,grep,find,ls） |
| 声明进模型 | 39 | **7** |
| 命令（含插件 slash 命令） | 33 | **33 —— 一字不差** |
| skills | 14 | 14 |

即：`full` 下插件**照样全装**（`/freeflow`、`/plan`、`/websearch`、`/mcp-adapter`、
`/notify`… 全在，provider / MCP 连接 / hooks / skills 照旧），**只有工具注册被
allowlist 挡掉**（computer_use、agent_browser、hashline、web 工具一个都不注册，
codemode 也不声明）。`find` 在、`glob` 不是 pi 工具。

**现行档位语义真相**（= 「更精准」的出发点）：所有预设只切**声明轴**，
**装载轴永远全开**（除非全局 `load_extensions` 关）：

| 档 | 装载轴 | 声明轴 |
|---|---|---|
| `configured` | 全装 | 不切（pi 按 `defaultTools` + 插件默认激活自己算 → 39） |
| `full` | 全装 | 切成 7 |
| `default` / `read-only` | 全装 | 切成 4 |
| `chat-only` | 全装 | 0 |
| `full+plugins` | **会话插件集**（唯一动装载的档） | full 7 ∪ pi 自己激活的 |

⇒ 现在既没有「最小装载」档，也没有「全能力 + 可控声明」档；034 的精细化就是
把两轴各自显式化。

### 1.2 核心约束：插件提示词注入与工具声明会不一致（嘴手一致规则）

**用户实拍 + 会话文件回放证实**（`role:"system"` 的 `sections` 按序回放）：

| 会话 | 声明工具 | 系统提示词总字符 | 其中 `agent_browser` 注入 |
|---|---|---|---|
| `full` 档（截图那个） | **7**（bash,read,write,find,ls,edit,grep） | 53,589 | **36,417 字符 = 67%**（截图的插件 9,104 token/58% 就是它） |
| `full+plugins` 冒烟（只选 pi-web-access） | 12（7 内置+codemode+4 web） | 17,628 | **0**（包没装载 → 没注入） |

机制：

- 插件注入是**独立的命名 section**（`sections.agent_browser`，由
  `agent-browser/index.js` 拼 `PROJECT_RULE_PROMPT` + guidelines），**与工具注册
  完全解耦**；
- pi 自己的 core section 会按 allowlist 自适应（`full` 的 `rules` = 1,083 vs
  `configured` = 5,627，`tools` 段只含 7 个），**插件却感知不到自己的工具被掐**；
- 工具带 `namespace{name, description, instructions}`（agent_browser 一族 8 个工具
  共享 namespace `browser`，其 instructions 明写「Full browser instructions remain
  in the agent_browser prompt section」），命令带 `sourceInfo{path,origin,baseDir}`
  → **工具/注入 ↔ 插件身份的映射材料是现成的**。

**违反面**：`full` / `default` / `read-only` / `chat-only` 四个档全部违反 ——
插件全装（注入照来）+ 工具全掐。`chat-only` 最极端：0 个工具，系统提示词里却有
36KB「优先使用原生 agent_browser 工具」。危害不止浪费上下文（58%）：模型会去
调用**不存在的工具**（幻觉 tool call / 报错 / 绕路 bash）。

**规则（档位设计必须满足）**：*系统提示词里推荐的工具，模型必须真的能调用*
（`注入 ⊆ 声明`）。三条满足路径：

1. **收窄装载** —— 不装该插件则无注入（`full+plugins` 天然满足，冒烟 0 注入 ✓）；
2. **装载但抑制注入** —— `before_agent_start` 可改 `systemPromptOptions` 的
   prompt sections（extensions.md 背书；bundle 里 handler 返回
   `{messages, systemPromptOptions}`）→ activate 扩展删掉「其工具未声明」的
   section，保留命令/provider/MCP。**待实测**（能否按 section 名删）；
3. **声明全集** —— `full` 不再掐工具（= `full+plugins` 全选），代价是 39 个工具
   的说明噪声回来。
## 2. pi 提供的粒度开关（可用的杠杆）

| 杠杆 | 粒度 | 说明 |
|---|---|---|
| `-e/--extension <路径\|包>` | 扩展（文件/目录/包） | 包 = 该包全部资源；文件 = 单个扩展 |
| `--skill <路径>` | 单个 skill（目录/SKILL.md） | R1 实测：`-ne -ns -np --no-themes --skill ~/.pi/agent/skills/jev` → 只剩 `skill:jev` |
| `--prompt-template <路径>` | 单个提示词模板 | 同上（repeatable） |
| `--theme <路径>` | 单个主题 | 同上；**注意主题不在 `get_commands` 里**，库存要另找 |
| `-ne / -ns / -np / --no-themes / -nc` | 全局隔离 | 关掉「发现 + 配置」的那一类资源，显式路径参数仍然生效 |
| 扩展 `setActiveTools(名单)` | **进模型的工具集** | R2 实测：插件全注册（23 个工具）而 active **精确 = 点名的 4 个** |
| settings 资源数组（`!`/`+`/`-` glob） | 仅 settings 作用域 | 用户级相对 agent dir、项目级相对 `.pi`；**不能当会话参数用** |

**库存来源**：活进程 `get_commands` 每条带 `source`（`extension`/`prompt`/`skill`）与
`sourceInfo{ path, scope, origin: "top-level"|"package", baseDir }` —— 等于 pi 自己
把「装了哪些资源、各自属于哪个包」报出来，不需要复刻 pi 的发现规则（npm/git/本地包的
约定目录、manifest 过滤、glob 取反…）。`pi list` 另外给出每个包的安装路径。
缺口只有一个：**主题没有对应的命令，拿不到 path**。

## 3. 设计空间（四层，正交）

```
① 资源装载   装哪些扩展 / skills / 提示词 / 主题        （包级 → 资源级别）
② 工具声明   哪些工具写进模型上下文（active）            （现在被 --tools 一刀切）
③ 作用域     会话 / 项目 / 全局默认 + 持久化
④ UI 信息    选了之后到底会发生什么（工具数、资源计数、provider）
```

现状与目标：

- ①：`full+plugins` 已能按会话选**包**；资源级别（每包 × 四类，或单文件）尚无。
- ②：`configured` = 全量 39 个；带 `--tools` 的档 = 插件工具干脆不注册。
  **缺一档「插件都在，但只声明我要的工具」**——R2 已证明技术上现成。
- ③：`tools_preset` 与 `ext_sources` 都不落盘，重启回落 `configured` + 全局插件集。
- ④：选择面板目前只有包名（可加资源计数、provider、预计声明工具数）。

## 4. 推荐路线（三步，各自独立可用）

### S1（已完成）会话级**包**选择 = `full+plugins`
`-ne -e <选中包…> -e builtin:<settings 里开着的> -e full_activate.ts`，
`full_activate` = `full 内置 ∪ getActiveTools()`（保留 pi 自己激活的
deferred/codemode 语义）。见 031 文档与 `session/tools_recipe.rs`。

### S2（推荐下一步）会话级**工具声明**名单 —— 插件都在，工具只声明要用的
把 `full_activate.ts` 泛化成「按名单声明」：

```
PROBE_KEEP="read,bash,grep,anchor_grep"  →  active 精确 = 这 4 个（R2 实测）
```

落地方式：扩展读一个随 spawn 传入的名单文件（或环境变量），
`session_start` 时 `setActiveTools(名单 ∪ pi 自己激活的项 − powershell)`。
UI：工具胶囊菜单里每个档显示「本会话声明 N 个工具」，并给一个
「按插件分组勾选工具」的子面板（分组数据来自包名 + 工具名）。
收益：默认档从 39 个说明降到 N 个；插件 provider/命令/skill 照常可用。

### S3（按需）资源级别 + 作用域/持久化
- 资源级：`--skill` / `--prompt-template` / `--theme` / `-e <文件>` 显式路径 +
  `-ne -ns -np --no-themes` 隔离；库存走活进程 `get_commands`（主题另扫）；
- 作用域：会话 → 项目（`<cwd>/.pi/…`）→ 全局默认（settings 页）三级，
  会话级选择落会话元数据（或 app 记忆），不再每次重生都回落全局。

### 1.3 为什么 `full` 走「不装载」而不是「装载 + 抑制注入」

pi 的扩展加载顺序（bundle `chunk-33XOIQ5N.js`）：

```js
extensionPaths = this.noExtensions ? cliEnabledExtensions
                                   : this.mergePaths(cliEnabledExtensions, enabledExtensions)
// mergePaths(primary, additional) = [...primary, ...additional]
```

⇒ **CLI `-e` 排在包前面**；`before_agent_start` 的 handler 按扩展加载顺序跑 ⇒ 我们的
`-e` 抑制器**先跑**，包后跑并写回（agent-browser 就是这么注入的：
`event.systemPromptOptions.sections.agent_browser = fullInstructions(ctx)`）。`-e` 又
没法排到包后面，所以「装载 + 抑制」在 `full` 上不可靠（`forceSystemPrompt` 能让模型
拿不到，但 transcript 仍记录 sections ⇒ 面板照样显示 36KB，语义更绕）。

**定稿**：`full` = `-ne`（包一个不装）+ 显式 `-e` 加回**个人扩展**
（`<agent dir>/extensions/*`，如 pi-notify）+ `-e builtin:<settings 里开着的>` +
`--tools bash,read,edit,write,grep,find,ls`。结构性零插件注入；个人扩展不受影响；
skills / prompts / themes 本来就不受 `-ne` 管辖（个人 skills 照常）。
代价：`full` 档没有包的命令 / provider / MCP（freeflow 模型要在「自定义」里选）。

实现：`pi_link::extensions::personal_extensions()`（复刻 pi 发现口径：顶层 `*.ts`/`*.js`、
一级子目录的 `pi.extensions[]` / `index.ts` / `index.js`，**不递归**）+ `tools_recipe::full_args`。
