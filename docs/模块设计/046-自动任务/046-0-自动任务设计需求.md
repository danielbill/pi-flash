自动任务由两部分构成：
1、定时调度服务
2、任务管理模块

「自动任务」仅是用户可见的功能名;内部 = 定时调度(共有服务)+ 任务(业务模块)两个正交件。
调度只懂时间不懂任务,任务只懂业务不懂轮询。总设计见 [046-自动任务.md](./046-自动任务.md)(UI 唯一事实源 §1 / 开发计划 §2)。

## 定时调度服务

**代码位置**:`crates/app/src/services/scheduler.rs`(共有服务,不属 046 专属;后续闲时队列等周期类需求同泵注册,不另起 timer)

**功能清单**:
- 唯一 timer,20s 一 tick;ticking + tickRequested 两变量合并去重(tick 进行中到来的唤醒不丢弃,本轮结束立即补跑)
- `ScheduleSource` 注册表:source 实现 `id / recover(now) / claim(now, in_flight) → Vec<DueJob> / execute(DueJob) → oneshot / settle(job, outcome, now)`,实现方经 startup 注册
- in-flight 集合:已派发未结算的作业,claim 时传给 source 防重复派发
- 启动时逐 source 调 `recover()`(source 自清上个实例残留的 running 态)
- 作业结算后统一 `cx.notify()` 驱动 UI 刷新
- misfire 宽限等通用判定以纯函数 helper 提供(如 `misfire_grace(next_run, now, 5min)`)

**不做**:无存储、无业务语义、无 dev-flag——空注册表时泵空转成本≈0(20s 查一次)

**启动时序**:`shell/startup/` pumps 拉起(挂 pumps 链,先于任何 source 派发;startup 时先跑全部 source 的 recover 再开 timer)

**存储**:无(调度器自身零表;source 的账 source 自己管)

**log**:`[scheduler]` 前缀:启动/停止、每次 tick 的认领/结算条数(仅变化时记,防刷屏)、source 注册/移除、recover 清理条数

## 任务管理模块

**代码位置**:`crates/app/src/tasks/`(state + store + run 三件,impl Chat 块接线;实现 ScheduleSource 注册进调度服务);UI 弹窗落 `crates/app/src/dialogs/`(大卡三 tab,§1);psp 入口钮在 function_panel/psp;存储层走 pf-context TaskStore(`crates/pf-context/src/domain/tasks.rs` 种子扩展)

**功能清单**:
- 任务 CRUD:创建/编辑(同表单预填)/启停/删除(删运行中先中止);上限 20 条(创建事务内 COUNT)
- spec_json schema:`kind: script|agent` + `schedule{unit,interval,hour,minute,weekdays,month_day}` + 业务字段;反序列化即校验,非法拒写
- next_run 计算:五档周期(每分钟/每小时/每天/每周/每月)chrono Local 直算;anchorAt 锚点防漂移(minute 档不对齐墙钟刻度;改周期重锚,改其它字段保锚)
- 调度接入:claim 流程——due(enabled ∧ next_run_at≤now)→ in-flight 则落 skipped run → misfire 判定(5min 宽限内照跑,超出 skip 不补跑、next_run 前推)→ 交调度服务派发;settle 重算 next_run_at
- 执行链:agent 任务每次触发经 session/runtime 新建会话(model/tools/thinking 覆盖或继承,prompt=task.desc,run 记 session_path);脚本任务走 services/script_exec 子进程(cwd=脚本所在目录,30min 超时强杀,输出尾+exit code 写 result_json)
- 立即运行:trigger=manual,只写 run 不动 next_run_at/周期;运行中再触发被 claim skip
- 运行历史:每任务保留最近 50 条(后台 prune);任务删除则相关日志连带删除;历史行按 outcome 四态(ok/failed/timeout/skipped)+running spinner 展示
- recover(启动扫描):task_runs 中 outcome='running' 残留 → 置 failed(app_exit 中断)
- dev-flag `auto_tasks`(默认关):门 UI 入口钮/弹窗/source 注册三处同源;共有泵不受其管

**启动时序**:startup pumps → 调度服务 recover → tasks source 注册 + 自身 recover(running 残留置 failed)→ 进正常轮询;首次 tick 前 UI 侧(TaskStore 读任务列表)已完成,泵只追加状态

**存储**:SQLite(rusqlite bundled,复用 pf-context):
- `task_defs`(id/title/spec_json/enabled/next_run_at/anchor_at/created_at/updated_at)——任务定义 + 调度指针
- `task_runs`(id/def_id/trigger/started_at/finished_at/outcome/session_path/result_json,索引 def_id+started_at DESC)——运行历史 + 结算台账
- 未发布免迁移,种子建表直接扩列

**log**:同域前缀 `[tasks]`:任务创建/编辑/启停/删除、每次派发(task+trigger)、运行结算(task/outcome/耗时)、misfire skip、prune 条数、recover 清理条数;错误(会话创建失败/脚本起进程失败/DB 写失败)error 级带 task id

## 任务完成/失败通知
PF当前没有统一的消息管理中心。
Task运行结束或运行异常中断暂时只在「任务中心」的列表上简单标识，不做额外推送。

## 运行日志存储限制
1、每任务保留最近 50 条。
2、任务删除则相关日志连带删除。

**触发**:tasks source 内置 prune job——启动 recover 时跑一次 + 泵每小时 tick 顺带跑一次(计数器到点执行)。对齐 ZCode 反教训(pruneRuns 定义了但从未接线,automationRepo.ts:1483),**API 必须真挂泵**,不提供无人调用的删除接口。

**SQL**(事务内,TaskStore.prune_runs(keep=50)):先查超量 def 列表(任务≤20,循环开销可忽略),逐 def 删除按 started_at DESC 编号 >50 的行。

**边界**:只删 `task_runs` 台账行,**不动 agent run 对应的会话文件**(用户资产;历史行仍可 open_session 重开,§1.4;会话本体生命周期归 052 会话清理)。删除量小(单任务每小时新增个位数条),WAL 下无压力;删除条数进 `[tasks]` log。

**UI 语义**:无(§1.4 已注明不进 UI)——历史行自然消失,无删除提示。
