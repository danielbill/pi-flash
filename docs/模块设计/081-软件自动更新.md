# 实现（2026-10-11 落地）

## 0. 模块与职责分界

- **exe（`services/updater.rs`，727 行）**：检查 / 下载 / 校验 / 解压 / 写 staging
  —— **从不碰 `payload/` 本体**（自己的 exe 在里面，锁死）
- **薄壳启动器（`npm/bin/pi-flash.js` + `lib.js`）**：swap 落位（旧进程已退出、
  目录无锁）+ 自愈兜底；e2e `npm/test/e2e.js` 新增 ⑩⑪
- 协作前提：exe 与薄壳**同版本同发布**（release.sh 三处版本单点同步）——
  有自动更新能力的 exe 必然配着认识 swap 的启动器，无旧启动器适配问题

## 1. 落位协议（exe ↔ 启动器）

```text
<pkg>/payload/                  当前载荷（运行中，不可整删）
<pkg>/payload.stage-<ver>/      新载荷（exe 解压后 rename 而来，含 .payload-version 戳）
<pkg>/update-staged.json        标记 {"version","staged_at"}（tmp+rename 原子写）
```

- 标记读取校验：staging 里有 `pi-flash.exe` **且** `.payload-version` 戳吻合，
  否则标记与 staging 一并清掉（半截下载自愈）
- swap（启动器）：`rename payload→payload.old-<ts>` → `rename staging→payload`
  → 删标记 → 删 old；旧实例占用（EBUSY/EPERM）→ 本次跳过，标记留待下次；
  swap 半途失败把 old 搬回兜底
- 自愈语义变更（080 §3.1）：戳 == 包版本 或 **戳 > 包版本**（应用内更新先行，
  薄壳还是旧版）都算可信；**戳 < 包版本才重下**——杜绝降级循环

## 2. 检查与下载

- 端点：`api.github.com/repos/danielbill/pi-flash/releases/latest`（tag_name + body）；
  资产 `<mirror|github>/releases/download/v<ver>/pi-flash-<ver>-win32-x64.zip` +
  sidecar `.sha256`（404 回落 `SHA256SUMS`，080 §3.2 同序）
- 纪律：检测 timeout 30s，失败重试 2 次、间隔 10 分钟，最终失败静默回落；
  下载 3 次尝试 + 线性退避，连接超时 30s / 整体 30min；全程后台线程
- 校验通过才解压（边下边算 SHA-256，单遍）；zip 条目名安全化（拒绝对路径/
  `..`/盘符）；版本比较 x.y.z 逐段数值（`version_gt`，单测覆盖）
- release body 随下载落 `~/.pi-flash/changelog-cache/<ver>.md`（重启后的
  更新日志页直接读本地；缺失再按 `releases/tags/v<当前>` 现拉一次）

## 6. 已知边界

- **单实例假设**：同时开两个 PF 都在下载 → staging rename 同名目录，后到者
  覆盖（内容一致，无害）；标记原子写
- **npm 目录只读**（Program Files prefix 提权安装）：staging 写失败 → 静默回落，
  下次启动再试；不弹错
- **macOS**：Rust 侧校验只认 `pi-flash.exe` 布局（win32-x64）；macOS 分发已停
  （AGENTS.md 铁律），届时按 `exeRelPath` 对齐
- **off 模式不取消进行中的下载**：开关只影响下一次检查；已开始的下载照常落
  staging（重启后生效）
