# 升级 vendored pi 0.87.1 → 1.0（对接新 model 列表接口）

## 前提结论（已与用户确认的三问）
- 发布包自包含：exe + node.exe + vendor/pi（pi core = JS bundle）
- 调用方式维持 RPC（spawn `node cli.js -ne --mode rpc`），不引入 SDK
- node 依赖：编译不依赖；开发期用 PATH 系统 node；发布版用内置 node.exe——本计划不改变这三点

## 步骤

1. **诊断当前断点**（先于升级，用 pi-link 现有 `live_rpc_probe.rs` 模式写一次性探针）
   - 跑 vendored 0.87.1 的 `get_available_models`，确认「model 列表空」断在哪层：RPC 无响应 / 返回结构变 / `parse_model_list` 解析为空
   - 留意 `~/.pi/agent` 已被系统 1.0 迁移过（新增 `models-store.json`、settings.json 有 1.0 字段），0.87.1 读到的配置可能已损坏

2. **锁定 1.0 目标版本**：`npm view @earendil-works/pi-coding-agent versions` 取最新 1.0.x（与用户系统 pi 对齐）

3. **bump vendor**：
   - `vendor/pi/package.json` 0.87.1 → 1.0.x
   - `cd vendor/pi && npm ci`
   - 同步 `vendor/pi/VERSION` 与 `crates/pi-link` 的 `PI_VENDOR_VERSION`（vendor.rs 有断言测试守着）

4. **协议符合性验证**：`cargo test -p pi-link` 全量跑；重点对比 1.0 的 `get_available_models` / `set_model` 响应结构与 `protocol.rs` 解析器的预期

5. **修复差异**：按诊断结果改 `protocol.rs` / `session/runtime.rs`（如 1.0 改用 models-store 结构或新增字段）；改模型下拉/选择 UI 所需的字段映射（`models_config.rs` / `runtime.rs:336` 附近）

6. **`-ne` 维持不动**：vendored 分发自包含原则不变；「1.0 后是否放开扩展加载」是独立后续话题，不在本次范围

7. **烟测 + 交用户实测**：`scripts/dev.sh` 跑通模型列表加载、会话、工具调用；按既定规矩停下交用户验证（不 SendInput 驱动 UI）

8. **小步提交**：诊断结论、bump、协议修复、UI 适配各一个独立 commit，方便回滚

## 风险
- 1.0 RPC 若有 breaking change，协议层改动量未知——此前论证协议面与 0.87 几乎零差异，风险低；探针先行，发现大改再回来同步
- `~/.pi/agent` 全局配置已是 1.0 形态，vendored 1.0 读它反而是对齐，风险低
- 发布链路（release.sh 内置 node + vendor）无需改动
