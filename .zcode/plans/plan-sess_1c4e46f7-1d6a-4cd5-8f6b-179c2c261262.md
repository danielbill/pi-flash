# 启动预加载方案(会话内容预加载 + 加载深度确认)

## 调查结论(写入契约)

1. **pi-web 无跨项目预加载**。"切项目秒出" = ①页面内存 LRU(8 会话/32MB/10min,只存打开过的)+ ②服务端 SM 指纹缓存(12 个/256MB)+ ③**响应即 50 条可见尾窗**(pi-web route 自截断,默认 50 cap 1000,toolResult 不占额,raw cap = max(200, tail×6);deferThinking=240 字符预览 / deferMedia=图片转 URL / tree=summary 三重瘦身)。
2. **pi 本体无窗口**:SessionManager.open 全量解析文件(小会话 ~150ms,82MB ~1.1s);get_messages 返回**投影全量**。投影 = compaction 感知活跃分支消息(自动压缩后 = 摘要检查点 + 压缩点之后的消息)——2000 条消息的会话,活跃投影通常远小于 2000,对账成本可控。
3. **偏差记录**:pi 投影是分支感知的;pi-flash 的 read_tail_messages 是物理尾行近似(可能含废弃分支条目)——对"尾窗预渲染"足够,渲染后由 RPC 投影对账校正。

## 实现设计

**① 设置参数**(services/workspace.rs AppSettings):新增 `preload: Option<usize>`,键名 `preload_sessions`,缺省 10,0=关闭;读写两端对称(原子写+进程缓存已有)。

**② 尾窗转换纯函数**(session/messages.rs):`msgs_from_tail(values: Vec<Value>) -> Vec<Msg>` — 复用 content_blocks/Usage::parse 同款解析;open_session 内联 ingest 循环改用它。

**③ 内存尾窗缓存**(Chat 新字段):`session_tail_cache: HashMap<PathBuf, Vec<Msg>>`,容量上限 = preload 值。

**④ 后台预加载**(Chat::new 现有后台填充任务内、sessions 列表落地后):`list_sessions(preload_n)` 全局最近会话(跨项目,mtime 新→旧)→ 跳过当前 active → 逐个 read_tail_messages(256KB,100) → msgs_from_tail → 入缓存;超 N 即停。open_session 未命中时回填自身尾窗(容量满则清空重建;陈旧无害,见 ⑥)。

**⑤ 打开命中**(open_session):先查缓存——命中→批量追加 Vec<Msg>(无磁盘读、无转换);未命中→现有磁盘直读路径并回填。GetMessages/GetTree RPC 照发。

**⑥ 顺带修真 bug**:on_event 的 get_messages 分支 ingest 全量前 `self.messages.clear()` + list reset——预渲染消息被权威投影**替换**而非叠加(修复消息翻倍)。

## 不做的事(记录)
- 不模拟 pi-web 的 SM 全量解析缓存(我们只读尾窗,天然更快);
- get_messages 投影 ingest 的深度优化(超大投影解析抖动)留 G+:可用尾窗 + get_entries since 翻页替代;
- 分支感知的尾窗投影(剔除废弃分支)留 G+,先靠 RPC 对账校正。

## 验收
- cargo test(app+pi-link)全绿;msgs_from_tail 单测;
- 实测:启动后切到另一最近项目,其最后会话消息立即上屏(缓存命中),pi 就绪后对账无重复;
- app_settings.json 手改 preload_sessions=0 时预加载关闭。
